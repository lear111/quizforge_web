# Local rule execution

The Java service targets Java 21. Run `npm ci --ignore-scripts` with Node 24 before starting the runnable Maven jar; `ajv` is pinned to 8.20.0. The jar still needs the `web`, `server`, `node_modules`, `extensions`, and `question-banks` directories beside the configured `--root`.

The Java entry point supports `--root`, `--host`, `--port`, `--token`, and `--node`. Its defaults are the current directory, `127.0.0.1`, port 8080, no token, and `node`; the supplied Windows startup scripts use port 8787 by default. A configured command-line token protects API endpoints through `X-QuizForge-Token`, except the password/token login exchange; the public entry page can receive a fragment token. The Java service does not persist command-line tokens. Browser writes require the same origin, and non-browser JSON clients may omit `Origin`.

The normal loopback service exposes local `GET/PUT /api/settings/network`. Management requires the main listener, loopback peer and loopback Host; LAN clients cannot change these settings. PUT accepts `{enabled,port,password?}`, GET and successful PUT return `{canManage,enabled,port,passwordConfigured,urls,error?}`. Enabling starts a second LAN listener (normally port 8788) sharing the same state store; disabling closes it. Settings persist in `.state/network-settings.json` with a salted PBKDF2 password verifier, never the plaintext password. Restart restores the LAN listener, reporting a binding failure through the settings response while keeping the local service usable. These settings do not modify the OS firewall.

`POST /api/auth/login` exchanges `{password}` for `{token}` after origin validation and rate limiting. LAN API calls require a short-lived random session token. Password changes or disabling the listener revoke its sessions. An initial password has at least 8 characters; omitted/empty password preserves the existing verifier. Local service access stays unchanged. Legacy command-line token mode remains supported by the login endpoint and is separate from the persistent LAN settings. All devices still share practice state and history.

Every rule invocation starts a fresh child with an eight-second process deadline (including Node startup and schema compilation), a 96 MiB V8 old-space limit, an 8 MiB input limit, a 2 MiB output limit, and a 64 KiB stderr limit. The child inherits only basic OS path/temp variables. Node filesystem permissions, when available, allow only the runner, its npm dependencies, and the three declared rule/schema files. The VM has no direct `process`, `require`, `fetch`, or filesystem API, disables dynamic string/Wasm code generation, and bounds each VM invocation to 650 ms. The Node flag limits V8 heap rather than total operating-system process memory. Only local administrator supplied extensions are supported: this is not a full hostile-code OS sandbox.

Rules register `QF.defineType({ project, validateQuestion?, validateAnswer?, grade, getScore? })`. Optional validators use `validateQuestion(data)` and `validateAnswer(answer, data)`; returning `false` or throwing rejects the input. `grade(data, answer)` returns finite bounded score/maxScore, boolean correct, and JSON feedback. Optional `getScore(data,state)` returns `{score,maxScore}` with finite `0 <= score <= maxScore`; `state` includes status, answer, result, revision and a `submitted` boolean. The runner batches these calls; unsubmitted questions contribute zero earned points but their maximum remains in the whole-bank total. Existing single-choice 1.0.0 is adapted by the runner using submitted result scores or unsubmitted `project(...).maxScore`, without changing its frozen package. Missing/invalid score output fails explicitly. AJV draft-07 schemas validate raw questions and answers first. Practice/example responses contain only `project(data, { submitted, result })`, and historical views use frozen public projections, including unsubmitted questions. Explicit editor responses contain raw data for authoring; Java and the host contain no question-type branches.

Only manifest-declared page assets are returned by the extension page API. Static serving is restricted to normal files inside `web/` with explicit browser asset extensions. Banks, rule files, schemas, state, arbitrary paths, and symlinks are never static resources. Catalog rescanning checks manifests and declared asset changes; malformed entries are isolated.

Question responses and successful action responses include `stamp: {revision, contentVersion, packageVersion}` and authoritative `extension: {id, version, name}` metadata for that question. `GET /api/collections/{kind}/{id}/questions/{qid}/stamp` returns this small object without projecting the question. After an unchanged library has been loaded, this path scans file metadata, checks state compatibility, and reads revisions without starting Node. The initial scan and a detected library change still validate banks through the rule engine. Question-row metadata includes `type: {id, version, name}` from its effective extension. Legacy banks keep their root default; mixed banks may declare an exact extension reference per question.

`RuleBatches` groups validation, projection and score inputs by extension ID/version/fingerprint, runs sequential chunks of up to 512 inputs with a 512 KiB target byte budget, and restores the original question order. An oversized single item remains subject to the existing child input/output limits. Mixed round snapshots store one `pages[pageKey]` per extension version, identified by frozen ID/version/fingerprint; question entries reference `pageKey`. Legacy `round.page` and their state identities remain readable. This upgrade introduces no worker pool or background iframe instances.

`contentVersion` binds a question's data, title, collection identity, and extension package; `packageVersion` binds only the extension package and is shared across its questions. Both are opaque HMAC values using a random in-memory server key, so the cache API cannot expose an unkeyed digest that clients could use to guess hidden answers. Restarting the service invalidates browser cache versions. Revisions change for all confirmed answer and whiteboard writes. Stamp requests retain token checks, `no-store`, and the same `COLLECTION_CHANGED` refusal as full reads. Idempotent action replay preserves its original full response, including its original stamp; a later freshness request compares against current state. Browser caches must be revalidated with this endpoint before reuse.

Action requests may include a `contentVersion` precondition taken from the displayed question's stamp. After exact receipt replay is checked, a stale version returns `409 CONTENT_CONFLICT` before grading or writing, including when a previously unanswered question still has revision zero. Capture the version with the action and retain it for identical network retries. The field remains optional for older API clients.

Practice state is stored under `.state/` in collection-key hashes. Real banks and extension previews use separate keys. Each write uses a temporary file, flush, and atomic replacement; an unsupported filesystem or failed write returns an error and preserves the previous state. Corrupt state is reported without replacing it. Revision guards cover answer and whiteboard writes. Persisted replay receipts preserve the exact confirmed response after restart; each question retains at most 32 receipts, trimmed to approximately 16 MiB, while a collection state file is capped at 32 MiB. Reusing a retained request ID with different JSON fails with 409. Retry clears the answer/result and preserves per-question ink.

The Java state cache holds at most eight recently used collections and at most 64 MiB of their encoded JSON sizes. The byte budget is an encoded-size accounting limit, not a total Java heap guarantee. Old entries are evicted from memory only; disk state and replay receipts remain intact and reload on the next access. Serialized byte counts from writes and file sizes from reads are reused for accounting without serializing large state a second time.

Saved question data is bound to a canonical JSON content fingerprint and the fixed-version extension fingerprint (manifest, rules, schemas, and practice page assets). Manually changing a saved question or the same-version practice extension returns `409 COLLECTION_CHANGED` before projecting answers, replaying receipts, or writing state; previous state bytes are preserved. Changing question order or titles manually remains compatible. Nonempty legacy state without signatures is refused because its original content cannot be verified. The explicit edit API below safely updates a bank and only its modified question; unverified external file changes still require a new bank ID or extension version.

## Collection-round history

`GET /api/collections/{kind}/{id}/summary` returns `{score,maxScore,submittedCount,questionCount,finished,status,roundId,summaryVersion,questions:[{id,score,maxScore,submitted}]}`. The host renders its own summary card after the last question. `POST .../finish` accepts `{requestId,roundId,summaryVersion}` from that response and returns the saved summary plus `historyId`; roundId may be null before a round exists. It explicitly completes a round even with no/all/partially submitted questions, preserving a whole-bank `summary` and current saved ink. Identical requests are replayable; stale summary versions return `409 SUMMARY_CONFLICT`. Merely submitting every question no longer completes new rounds.

`GET /api/collections/{kind}/{id}/history` returns `{records:[...]}` newest first. Each record contains `id`, `createdAt`, `updatedAt` (UTC ISO timestamps), `status`, `submittedCount`, `questionCount`, `collectionTitle`, `extension`, `score`, and `maxScore`; explicitly completed records also contain the frozen whole-bank `summary`. Older/in-progress records without it retain their submitted-question totals. `GET .../history/{historyId}` adds `collection` (frozen question order and states), `questions:[{payload,page?}]`, and shared `page:{html,script,style}`. History routes do not require the current bank or extension to remain available. The host navigates within this frozen collection and enforces read-only interactions for both submitted/unsubmitted questions and the saved summary card.

`DELETE .../history/{historyId}` requires the same authentication and write-origin checks as other mutations, accepts no body, and returns `{deleted: historyId}`. It atomically removes that whole round from its saved state file, preserving current answers, ink, revisions, request receipts and all other history. Deleting an in-progress round means the next successful submission starts a new round. A missing record returns `404 HISTORY_NOT_FOUND`; clients can treat that as already removed when retrying after a lost response. Older saved extension versions remain deletable even if the live bank or package is missing. Legacy grouped records delete all constituent single-question snapshots; surviving legacy entries retain explicit round boundary metadata so IDs, order and grouping do not change after deletion.

The first submission freezes the collection and starts one round; subsequent submissions update that round until explicit completion through `finish`. Completing before the first submission creates and freezes a full-bank round directly. The next submission after completion starts a new round without copying previous results. Content edits seal an active round as interrupted while preserving its original questions; title-only edits leave it active. Submission/completion updates share the same atomic state replacement as practice and their request receipts. Exact replay neither duplicates a round nor updates its timestamps, including after restart. Pending whiteboard writes should be drained by the browser before submission or completion to include the newest ink. Histories are never silently pruned: the existing 32 MiB collection-state limit includes snapshots and frozen assets. Reaching the limit rejects the new write and preserves previous practice and history together.

Legacy per-question snapshots remain stored unchanged and are grouped at read time: consecutive distinct question IDs form one legacy record, and a repeated ID starts another. Only actually frozen questions are included, ordered by old submission time; unknown original questions or order are not reconstructed. Individual frozen pages are retained when they differ. Legacy records are marked incomplete because the former format did not save the full bank. History metadata spans saved versions of the same collection kind and ID.

## Generic question editing

Only `bank` collections support editing. `GET .../questions/{qid}/editor` returns `{question:{id,title,data},extension,revision,contentVersion,editor}`. This intentional editing endpoint exposes raw question data, including correct answers, through the same authenticated API. `editor` is `{html,script,style}` or `null`; this host reports a missing editor when absent. A local extension may add an optional `editor.json` sidecar declaring `entry`, `script`, and `style`. These three normal files are path-checked and capped at 1 MiB each. The editor capability is read separately and is excluded from the fixed practice-package fingerprint, so adding or modifying an editor does not invalidate existing practice.

`POST .../questions/{qid}/edit` accepts `{requestId,revision,contentVersion,title,data}`. Both guards are required. The replacement bank is validated by the declared generic schemas and validators before persistence. Changing raw question data resets only that question's current answer, result, and draft; its revision advances rather than returning to zero. Title-only saves preserve the current answer, result, and ink while advancing the revision. Other question state and every historical snapshot remain intact. The response is `{collection,payload}` with refreshed outline/state metadata and the current projected question. Up to 32 bounded collection edit receipts preserve exact successful responses; an identical request remains replayable after content changes and restart, and reusing an ID with different input fails.

Bank and practice files use a durable forward-only `.state/.edit-journal.json` transaction. It contains checksummed exact before/after bytes, uses flushed temporary files and atomic replacements, and verifies that targets contain only the original or planned bytes before completing. Interrupted edits recover on server startup or before subsequent collection/catalog operations. A pending transaction over unrelated manual changes is refused with evidence preserved. An I/O failure after journal creation returns `503 EDIT_PENDING`; retry the identical request after storage recovers. Do not manually remove the journal or overwrite either target during recovery.

Whiteboard writes are capped by the 8 MiB request limit and validated for schema, finite coordinates within ±1,000,000, zoom 0.25–4, hex colors, width 0.5–32, pressure 0–1, 2,000 strokes, 10,000 points per stroke, and 100,000 points total.

Validation commands: `mvn test`, `mvn package`, and `npm run test:rules`. Java tests use temporary directories and real HTTP endpoints; Node tests exercise schema validation, public projection, VM restrictions, loops, large output, and invalid grading.
