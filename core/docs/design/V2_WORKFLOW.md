# V2 开发流程

适用于 `v2` 分支的全部工作。与本文件冲突的旧约定不再适用。

## 1. 三个角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| 项目负责人 | 决定做什么、不做什么；试用并验收每个功能 | 读代码、读长文档 |
| Claude（审查） | 把需求整理成设计；审查有风险的改动；用大白话解释依据 | 替负责人做产品决定 |
| Codex（实现） | 写代码和测试；如实报告结果 | 自行增加需求或保护机制 |

## 2. 文档

| 文档 | 回答什么 | 谁改 |
|---|---|---|
| `V2_ARCHITECTURE.md` | 做什么：全部决定（D 编号）、数据格式、流程 | 只在负责人做出新决定时改 |
| `V2_WORKFLOW.md`（本文件） | 怎么协作 | 负责人同意后改 |
| `V2_PROGRESS.md` | 做到哪了，一页 | Codex 每合并一个功能后更新 |
| `V2_DATA_STRUCTURES.md` | 磁盘上存什么、每个字段为什么需要 | 改数据结构前先改它 |
| `V2_API_AND_STATE.md` | 前端与后端之间的接口 | 改接口时同步 |
| `../reference/V2_EXTENSIONS.md` | 拓展与宿主之间的接口，给拓展作者看 | 改接口时同步 |
| `V2_UI_PROTOTYPE.md` 与 `prototype/` | 界面长什么样：原型源码、颜色变量、每个界面元素的外观和状态 | 带界面的功能在设计第 ① 步更新；Codex 实现后改状态 |

其他文档（v1 计划、测量报告、被否决的设计、长篇设计说明）全部放在 `core/docs/design/archive/`，仅作记录，不需要阅读。各 PR 的记录放在 `core/docs/design/reviews/`，每份不超过一页。

## 3. 每个功能走同一条路

功能按"负责人能亲手试用的一件事"来划分（见第 6 节的清单），前后端一起做。

分两个阶段：先设计（负责人和 Claude 讨论），后实现（Codex）。**设计的四步全部写进文档之后，Codex 才开工。**

### 设计阶段

| 步骤 | 回答的问题 | 写到哪 |
|---|---|---|
| ① 行为 | 用户能做什么、不能做什么；有界面的，界面长什么样 | `V2_ARCHITECTURE.md` 的决定表；界面改在线原型，再更新 `V2_UI_PROTOTYPE.md` 与 `prototype/` |
| ② 分工 | 每件事由谁负责：拓展、宿主、还是后端 | 同上 |
| ③ 数据 | 要存什么、存在哪、每个字段为什么需要 | `V2_DATA_STRUCTURES.md` |
| ④ 接口 | 拓展与宿主之间、前端与后端之间各传什么 | `reference/V2_EXTENSIONS.md`、`V2_API_AND_STATE.md` |

顺序的理由：

- 行为在最前：后面每一步都以它为依据。
- 数据在接口之前：数据结构定了，接口基本就是"读哪一块、换哪一块"；先定接口，改数据时接口要跟着返工。
- 界面和行为一起定：原型在当前定稿版本上改，不另起新稿；行为写在决定表，外观写在原型说明的元素表，两边用 D 编号对应。
- 设计做完再实现：第 2 段里几处返工（位置文件、题型笔记、状态字段）都是因为决定晚于实现。

设计时用总览里的四条原则衡量（见 `V2_DATA_STRUCTURES.md` 第 0 节）：程序不理解题目内容；同一件事只存一份；小改动只写小文件；先做简单的，不为还没出现的需求写代码。接口按 `V2_API_AND_STATE.md` 开头的六条规则设计。

### 实现阶段

```
⑤ 验证   → ⑥ 实现   → ⑦ 检查   → ⑧ 试用   → ⑨ 记录
 Codex      Codex     CI + 审查   负责人     Codex
```

**⑤ 验证**：设计里有拿不准能否实现的地方（例如沙箱里的后台线程、把页面存成静态内容），先做一个小验证并报告结果，再全面实现。没有就跳过。

**⑥ 实现**：一个功能可以拆成几个 PR，每个 PR 只做一件事。实现中发现设计行不通或有遗漏，停下来报告，不自行改设计。

**⑦ 检查**
- 所有 PR：CI 三个 job 全绿。不跳过、不删除、不放宽测试。
- 高风险 PR（见第 4 节）：等 Claude 审查通过才合并。
- 其他 PR：CI 全绿即可合并。

**⑧ 试用**：功能合并后，Codex 给出试用步骤（怎么启动、点哪里、应该看到什么，五步以内）。负责人试用后回复"可以"或指出问题。负责人说可以，这个功能才算完成。

**⑨ 记录**：更新 `V2_PROGRESS.md`：状态、实测速度、遗留问题。

## 4. 高风险改动（必须审查）

- 作答的保存、锁定、分数保存、重做
- 历史和考试记录的存储
- 写入题库文件（编辑器、导入）
- 什么时候把答案（`solution`）发给前端
- 题型页面和评分环境的沙箱
- 登录鉴权和局域网访问

## 5. 决定权

**必须先问负责人：**
- 新增或去掉一个用户能感知的功能或行为。
- 新增任何"保护机制"：一种检查、一层缓存、一种兼容处理、一个限制。提出时必须用一两句大白话回答三个问题：防的是什么情况？不做会怎样？代价是什么（速度、复杂度）？
- 改动 `V2_ARCHITECTURE.md` 中的任何决定。

**Codex 可以自己定：** 代码结构、命名、测试写法、不改变行为的重构。

**原则：** 负责人看不懂的设计，默认是设计的问题。能用几句话讲清依据的才保留。拿不准时选更简单的做法。

负责人做出的每个新决定，由 Claude 写入 `V2_ARCHITECTURE.md` 并编号。口头说过但没写进去的不算数。

## 6. 功能清单与顺序

每一段做完，负责人都能亲手用到新东西。

| 段 | 做完后能做什么 |
|---|---|
| 1 | 打开题库，看到大纲，做一道单选题，提交并看到分数 |
| 2 | 多选、判断；草稿自动保存、白板、重做；切换题库并回到上次位置；刷新 |
| 2.5 | 题型接口定稿；清点并删除 v2 不再使用的 v1 代码和测试。不做题库转换工具：负责人的题库由专门的对话直接改写成 v2 格式，开发期间继续用模拟题库测试 |
| 3 | 完成练习、汇总、历史 |
| 4 | 考试模式 |
| 5 | 简答题、AI 评分、人工改分；设置。带答题区的题型另行设计，排在本段之后 |
| 6 | 导入导出、Hub、题库编辑器、拓展开发模式 |
| 7 | 打包发布、整体性能复测 |

顺序可以由负责人调整。

## 7. 汇报格式

Codex 向负责人汇报时不使用内部编号和术语，固定四行：

- **现在能做什么**
- **怎么试**（五步以内）
- **实测速度**（只列用户能感知的操作）
- **需要你决定的事**（没有就写"无"）

## 8. 代码规范

目的只有一个：代码要让人读得懂、改得动。负责人、审查者和以后接手的人都要能读。

**由工具保证的**（自动格式化 + 规范检查，CI 里检查，不通过不能合并）

- 一行一条语句，不用分号把多条语句连在同一行。
- 行宽上限 100 个字符。
- 统一的缩进、引号、换行，由格式化工具决定，不手工争论。
- 没有用到的变量和导入、隐式的全局变量等常见问题由规范检查报出。

**工具管不了、靠自觉和审查的**

- **文件和函数不能太长。** 一个 `.vue` 文件约 150 行以内，一个普通源文件约 300 行以内，一个函数约 50 行以内。超过了先想是不是该拆。
- **名字要能看出含义。** 除了循环下标和很短的回调参数，不用一两个字母的名字。
- **不易理解的地方写注释，说明"为什么"。** 例如：这段检查在防什么情况、为什么先写这个文件再写那个、这个数字从哪来。"做了什么"代码本身能看出来的不用写。
- **一个函数只做一件事。** 检查、计算、写盘分开。
- **先做简单的。** 不写"以后可能用到"的检查、参数、字段和抽象；不为不会发生或发生了也无妨的情况加保护。确有需要时再加，并说明防的是什么。
- **不为了行数少而压缩代码。** 嵌套的三元表达式、一个表达式里做多件事、靠逗号和短路求值控制流程，都算。

**后端的目录结构**

```
core/server/v2/
├── app.js            启动：组装下面各层，开始监听
├── routes/           接口表：一行一个接口，按题库、题目、拓展分文件
├── middleware/       公共检查：令牌、来源、请求体、错误格式、计时
├── controllers/      处理请求：取出参数，调用 service，把结果发回
├── services/         业务规则：打开题库、保存、提交、评分、重做、完成、归档
├── repositories/     读写磁盘：题库文件、作答文件、笔迹文件、拓展与公共组件
└── utils/            通用工具：JSON、文件与缓存、错误、请求凭据
```

每一层只调用它下面的层：`routes → controllers → services → repositories → utils`。不反向调用，不跨层调用（controller 不直接读写磁盘，repository 里不写业务规则）。文件名带上所属的层，如 `bank.service.js`、`state.repository.js`、`question.controller.js`。新功能按这个结构各加一个文件，不新开平铺的文件。

**前端的目录结构**

```
core/frontend/src/v2/
├── main.ts           入口：创建应用、Pinia、路由
├── App.vue           外壳：顶栏、题库列表、大纲
├── router/           页面地址与页面的对应（Vue Router）
├── views/            页面：做题页、汇总页、历史列表、历史回看
├── components/       组件：题目区、切题按钮、保存状态、得分卡片等
├── stores/           状态与流程（Pinia）：题库目录、当前练习、界面提示
├── api/              对后端的请求：一个接口一个函数
├── services/         不属于界面的逻辑：装载拓展页面、评分环境、保存时机、
│                     请求排队、拓展文件缓存、白板接入
├── types/            类型定义
└── styles/           全局样式变量
```

调用方向：`views / components → stores → api 与 services`。组件不直接调用 `api`，`api` 和 `services` 不引用组件。页面之间用 Vue Router 切换，地址能表达"哪个题库、哪道题、哪一页"，刷新后回到原处。

**后端的写法**

- 后端用 Express。每个接口在路由文件里用一行声明（方法 + 地址 + 处理函数），打开路由文件就能看到全部接口，与 `V2_API_AND_STATE.md` 的接口列表一一对应。
- 访问令牌、来源检查、请求大小限制、错误答复的统一格式写成中间件，不在每个接口里重复。
- 处理函数只做三件事：取出请求里的参数，调用负责业务的模块（题库、作答、笔迹），把结果发回。业务规则不写在路由里。
- 请求内容由 Express 以原始字节接收，仍用项目自己的 JSON 解析（重复键检查、保留数字写法），不用框架自带的解析。

**前端的写法**

- **接口模块**：对后端的请求集中在一个模块里，一个接口一个函数，与 `V2_API_AND_STATE.md` 的接口列表一一对应。带令牌、错误转换、请求编号在这里统一处理。组件和状态模块不直接调用 `fetch`。
- **状态用 Pinia 集中管理**：题库列表、当前题库的概览、当前题目、保存状态、忙碌与提示各有归属的 store。组件从 store 读取状态、调用 store 的动作；不在模块顶层放可变变量充当状态。
- **组件之间只用两种方式沟通**：属性往下传，事件往上报（`defineEmits`）。不把函数当属性传入，不用 `defineExpose` 让外层调用内层的内部函数；需要多个组件协作的流程写在 store 的动作里。
- **一个组件一件事**：格式化之后约 150 行以内。超过了就拆。
- **模板按层级换行缩进**，一个标签一行；较长的条件和事件处理写成具名的计算属性或函数，不写在模板里。
- **样式跟着组件走**：用组件自己的 `<style scoped>`；只有全局的变量和基础样式放公共文件。
- **与拓展页面、白板、评分环境打交道的逻辑**保持为独立的普通模块（如 `page.ts`、`grading.ts`），由 store 的动作调用，不放进组件。
- 沿用的 V1 组件（题库列表、大纲等）在用到时按上面的规则调整接口，改动单独提交。

这些规范只约束 `v2` 相关的代码（名字带 `v2` 的目录）和之后新写的代码。沿用的 V1 模块（如白板）保持原样，不为了规范去改它们。

格式整理和功能改动分开提交：整理格式的 PR 不改行为，改行为的 PR 不顺手重排无关代码。这样审查时能看清每个 PR 实际改了什么。

## 9. 并行开发

设计和审查是串行的，实现可以并行。并行的前提是每条线只改自己的文件，线与线之间只靠书面约定对接。

| 线 | 范围 | 对接依据 |
|---|---|---|
| 后端 | `core/server/v2/`、后端测试 | `V2_API_AND_STATE.md`、`V2_DATA_STRUCTURES.md` |
| 前端页面 | `core/frontend/src/v2/`、浏览器检查 | `V2_API_AND_STATE.md`、`reference/V2_EXTENSIONS.md` |
| 题型拓展 | 各拓展自己的文件夹 | `reference/V2_EXTENSIONS.md` |
| 题库内容 | 题库文件夹 | `V2_DATA_STRUCTURES.md` 第 1 节 |

规则：

- 一个功能要同时改后端和前端时，先把接口写进文档并合并，两条线再各自实现。
- 不改别的线的文件。发现对方的代码或约定有问题，提出来，不顺手改。
- 改约定（数据结构、接口）必须先改文档并经负责人同意，再改代码。
- 每个任务在进度页占一行，自己的说明和记录写在自己的文件里，不往公共文件里追加长段内容。
- 生成的文件（前端构建成品等）不提交进仓库。

题型拓展和题库内容这两条线现在就可以并行；后端和前端页面两条线在前端重组完成后分开。

## 10. 不变的底线

- 后端不执行题库或拓展制作者提供的代码。
- 答案锁定之前，任何接口的响应都不包含 `solution`。
- 保存失败时不留下写了一半的数据。
- 不使用负责人的真实题库和真实数据，除非有明确授权。
- `main` 保持 v1，除严重缺陷修复外不改动。
