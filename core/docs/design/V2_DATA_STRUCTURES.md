# V2 数据结构说明书

记录 V2 存到磁盘上的每一种数据：长什么样，每个字段是什么，以及为什么这样设计。改动数据结构前先改这份文档。

相关文档：题库与拓展的总体设计见 [V2_ARCHITECTURE.md](V2_ARCHITECTURE.md)（文中的 D 编号指那里的决定表）；拓展接口见 [题型拓展开发说明](../reference/V2_EXTENSIONS.md)；前后端接口见 [V2_API_AND_STATE.md](V2_API_AND_STATE.md)。

## 0. 总览

```
某个题库文件夹/
├── bank.json                  题库：作者写的，程序只读（编辑器除外）
├── images/ audio/ …           素材
└── .qf-v2/                    作答记录：程序写的，作者不用管
    ├── practice/              当前这一轮练习
    │   ├── state.json         作答
    │   └── ink/<内容指纹>/<题号哈希>.json   每道题的白板笔迹
    ├── exam/                  正在进行的考试，结构同 practice/；没在考试时不存在（第 4 段实现）
    └── rounds/<轮次>/         历史：每轮一个只读的题库副本（第 3 段实现）
```

四条贯穿始终的原则：

| 原则 | 含义 | 理由 |
|---|---|---|
| 程序不理解题目内容 | `question`、`solution`、`answer` 由拓展定格式，程序原样存取 | 去掉规则校验后（D2），程序不需要也不应该懂每种题型的内部结构。这样新增题型不用改程序 |
| 同一件事只存一份 | 能从别的字段看出来的信息不单独存 | 存两份就可能对不上，对不上时谁也不知道该信哪份 |
| 小改动只写小文件 | 频繁变化的大块内容单独存放 | V1 保存慢的根源是"点一个选项，重写几 MB"。实测笔迹与答案同文件时保存从 19 ms 升到 473 ms（D33） |
| 先做简单的 | 不为还没出现的需求写代码，后期有需要再加（D46） | 多写的检查、预留的字段、提前的抽象都要维护，而且常常猜错方向。这次重做里删掉的东西（规则校验、题型笔记、多个版本号、历史索引）大多是这样来的 |

## 1. 题库：`bank.json`

完整规则见总体设计第 2 节，这里只说结构和理由。

```json
{
  "formatVersion": 2,
  "id": "…", "title": "…", "description": "…",
  "features": { "history": true, "exam": true },
  "listening": { "L1": { "src": "audio/part1.mp3", "title": "…" } },
  "outline": [
    { "title": "一、选择题", "items": [
        { "id": "q1", "listening": "L1", "parts": [
            { "id": "sub_q1", "label": "1", "maxScore": 2 },
            { "id": "sub_q2", "label": "2", "maxScore": 2 } ] },
        { "id": "q2", "label": "3", "maxScore": 2 } ] }
  ],
  "questions": {
    "q1": { "type": "quizforge.single-choice@2", "question": { … }, "solution": { … } }
  }
}
```

| 设计 | 理由 |
|---|---|
| `outline` 和 `questions` 分开、平级 | 打开题库时只需要大纲。大纲单独放，程序读它就能画出整个目录，不用碰任何题目内容 |
| 每道题拆成 `question` 和 `solution` | 提交前只发 `question`，提交后才发 `solution`。分成两块，程序按一个键就能取出该发的部分，不需要理解内容 |
| 大纲三层：分组 → 大题 → 小题，都用数组 | 数组的顺序就是显示顺序，不需要另外的排序字段 |
| 大题是最小的操作单位 | 提交、锁定、评分、重做都以大题为单位。小题只是大题内部的划分，这样后端只需要定位到大题（D：先不支持单独提交小题） |
| `id` 和 `label` 分开 | `id` 给程序用，用来对应大纲条目、题目内容和作答记录；`label` 给人看，随便写 |
| 满分 `maxScore` 写在大纲里 | 汇总和大纲判断对错都要用满分，放在大纲里程序不用读题目内容就能拿到 |
| 听力定义在顶层、引用在大纲 | 听力由宿主播放，不经过拓展；多道题可以共用一段材料 |
| `type` 的 `@` 后是拓展的主版本号 | 题目数据是按某个版本的拓展写的。新旧主版本可以同时安装，各用各的（D18） |
| 素材引用统一写成 `qf-asset:路径` | 程序扫一遍就能找出一道题用到的全部素材，不用理解题目结构 |

### 1.1 富文本内容（D54，待实现）

题干、选项、答案解析这类要排版的内容，在 `question` 和 `solution` 里存为一段 HTML 字符串。哪些字段是富文本由题型拓展自己定，程序不管；拓展拿到后交给富文本组件显示。

```html
<p>下列说法<b style="color:#c00">错误</b>的是</p>
<p style="text-align:center"><img src="qf-asset:images/fig1.png" width="320"></p>
<p>已知 $x^2 + y^2 = 1$，求 $x+y$ 的最大值。</p>
```

允许的内容：

| 类别 | 白名单 |
|---|---|
| 段落与标题 | `p` `br` `h1`–`h4` `blockquote` `hr` `pre` |
| 文字 | `b` `strong` `i` `em` `u` `s` `sub` `sup` `mark` `code` `span` |
| 列表 | `ul` `ol` `li` |
| 表格 | `table` `thead` `tbody` `tr` `th` `td`，可带 `colspan` `rowspan` |
| 图片 | `img`，`src` 只能是 `qf-asset:…`，可带 `alt` `width` |
| 链接 | `a`，`href` 只能是 `http:` `https:` `mailto:` |
| 样式（`style` 属性里） | `color` `background-color` `font-size` `font-family` `text-align` `line-height` `text-indent` `margin-left` `vertical-align` `width` |
| 公式 | `$…$` 行内，`$$…$$` 独占一行，内容是 LaTeX；要显示美元符号写 `\$` |

其余标签、属性、样式在显示时去掉，不报错。

| 设计 | 理由 |
|---|---|
| 用 HTML 而不是树形文档或 Markdown | 树形文档 agent 写起来又长又易错；Markdown 没有字号、颜色、对齐、合并单元格。HTML 两头都满足，浏览器还能直接显示 |
| 只认一种格式 | 两种并存，显示、编辑、检查都要写两套 |
| 白名单，而不是"去掉危险的" | 只放行认识的东西，漏掉的是功能而不是安全。题目页面本来就在不能联网的沙箱里，这是第二道保险 |
| 清洗用成熟的现成库 | 安全相关的代码不自己写 |
| 图片仍用 `qf-asset:` | 程序扫一遍字符串就能找出用到的素材，与原来的做法一致 |
| 清洗在显示时做，不在打开题库时做 | 程序不理解题目内容，不知道哪个字段是富文本 |

### 1.2 答题区（D55、D59，待实现）

答题区的设置写在 `question` 里，结构由拓展定，程序不关心；拓展读出后交给答题区组件。基础题型约定的写法：

```json
"answerArea": {
  "height": 400,
  "style": "lines",
  "images": [ { "src": "qf-asset:images/axes.png", "x": 60, "y": 40, "width": 320 } ]
}
```

| 字段 | 内容 |
|---|---|
| `height` | 初始高度，写满自动加长 |
| `style` | 纸的样式：不写为空白，`lines` 为横线纸。以后的样式加在这里 |
| `images` | 出题人摆好的底图图片，坐标和宽度按答题区自身的尺寸 |

宽度不写在题目里，由拓展的页面样式决定。

## 2. 当前作答：`.qf-v2/practice/state.json`

只保存"当前这一轮"里用户动过的题。没作答过的题库没有这个文件；没碰过的题不在文件里。

### 2.1 顶层

```json
{
  "formatVersion": 2,
  "contentFingerprint": "a3f9…",
  "lastQuestionId": "q2",
  "completedAt": null,
  "questions": { "q1": { … }, "q2": { … } }
}
```

| 字段 | 内容 | 理由 |
|---|---|---|
| `formatVersion` | 固定为 2 | 以后格式变化时能认出旧文件 |
| `contentFingerprint` | 做题时 `bank.json` 和所用拓展文件的指纹 | 下次打开时重新算一遍，和它比。不一样说明题库或拓展被改过，这一轮的作答整体作废（D27）。旧指纹必须存在磁盘上，否则程序重启后无从比较 |
| `lastQuestionId` | 最后一次作答的大题 | 下次打开时回到这里（D32）。只在保存答案、提交、重做时顺带写入，不为它单独写文件，所以只看不做不会产生任何文件 |
| `completedAt` | 完成练习的时间；缺省或 `null` 表示作答中，只有完成时才写入 | 有值表示这一轮已完成：全部题目已锁定，不能再提交和重做，只能修正分数和写白板（D40、D42）。完成后继续用这个文件而不另建文件，这样改分数沿用同一套接口，历史文件到归档时一次写完 |
| `questions` | 以大题 `id` 为键 | 保存时只替换其中一道题的条目 |

为什么放在题库文件夹里而不是统一的目录：作答记录跟着文件夹走，改名、移动、复制、删除都不需要程序去"认"它属于哪个题库（D19）。

### 2.2 每道题

```json
"q1": {
  "status": { "sub_q1": "correct", "sub_q2": "wrong" },
  "answer": { … },
  "result": { … },
  "submissionId": "…",
  "revision": 4,
  "receipts": [ … ]
}
```

| 字段 | 内容 | 谁写 |
|---|---|---|
| `status` | 大纲上各小题的显示状态 | 宿主（依据拓展的报告和评分结果） |
| `answer` | 答案 | 拓展定格式，程序原样存 |
| `result` | 评分结果 | 拓展的评分函数返回，程序检查后原样存 |
| `submissionId` | 提交凭证；未提交为 `null` | 后端 |
| `revision` | 版本号 | 后端 |
| `receipts` | 最近 4 次请求的凭据 | 后端 |

#### `status`

没有小题的题是一个值；有小题的题是"小题 id → 值"的映射。取值就是大纲的五种颜色（D38）：

| 值 | 含义 | 什么时候写入 |
|---|---|---|
| `unanswered` | 未作答 | 拓展报告该小题没有答案；重做后 |
| `answered` | 已作答，还没有分数 | 拓展报告该小题有了答案。提交后等待评分期间保持不变 |
| `correct` | 对 | 评分后该小题得满分 |
| `wrong` | 错 | 评分后该小题未得满分（含未作答的 0 分） |
| `ungradable` | 无法评分 | 评分出错、超时或结果不合格 |

理由：

- **为什么精确到小题**：大纲的格子是按小题画的。如果只存整道大题的一个状态，就必须另外再存一份小题的信息，两份各管一半。
- **为什么存"显示状态"而不是"流程状态"**：答案是否锁定看 `submissionId`，是否已评分看 `result`，这些不需要再存一遍。大纲真正需要、又无法从别处得到的，是每个小题答没答、对不对。
- **为什么答没答要拓展报告**：程序不理解 `answer` 的格式，看不出哪个小题有内容。
- **为什么要存下来**：重新打开题库时，程序直接读它画大纲，不需要先把每道题的拓展加载一遍。
- **为什么对错由宿主判断**：规则只有一条（得分等于满分为对），所有题型一致，不该让每个拓展各写一遍。

流程上的状态由其他字段得出：

| 想知道 | 怎么看 |
|---|---|
| 答案是否锁定 | `submissionId` 不为 `null` |
| 是否已有评分 | `result` 不为 `null` |
| 是否在等人工或 AI 评分 | `result.score` 为 `null` 且 `status` 不是 `ungradable` |
| 是否需要自动补评 | 已锁定但 `result` 为 `null` |

#### `answer`

拓展的 `getAnswer()` 返回什么就存什么，重新打开时原样交还。程序不解析、不校验。理由见总览的第一条原则。

#### `result`

```json
{ "score": 2, "parts": { "sub_q1": 2, "sub_q2": 0 }, "message": null }
```

| 字段 | 内容 |
|---|---|
| `score` | 整题得分。没有分数时为 `null` |
| `parts` | 有小题时各小题的得分，以小题 id 为键，合计等于 `score`。写法与 `status` 一致 |
| `message` | 没有分数时的说明，给制作者排查用，如"评分超时"。有分数时为 `null` |

不设单独的状态字段，四种情况这样区分：

| 情况 | 怎么看 |
|---|---|
| 还没评（会自动补评） | 没有 `result` |
| 已评分 | `score` 是数字 |
| 等人工或 AI 评 | `score` 为 `null`，且该题 `status` 不是 `ungradable` |
| 无法评分 | 该题 `status` 为 `ungradable` |

评分正常时不存反馈文字：拓展手里有得分和答案解析，自己就能显示"回答正确"之类的话。AI 评语在第 5 段另加。

后端只检查：分数是有限的数、在 0 到满分之间、小题得分合计等于总分。理由：评分在前端进行（D3），后端不运行拓展代码，但要防止一个有缺陷的评分函数写入明显不合理的分数。

#### `submissionId`

提交时后端生成的一个随机编号。评分上报时必须带上它，对得上才接受。

理由：评分在前端、是异步的。如果用户提交后马上点了重做又重新提交，前一次的评分结果可能晚到。每次提交的编号不同，晚到的结果编号对不上，就不会被贴到新答案上。

#### `revision`

每写入一次加一。前端保存时带上"我是基于第几版改的"，后端发现不一致就拒绝。

理由：这是不用数据库的乐观锁，用来发现两个标签页同时改同一道题。

#### `receipts`

最近 4 次请求的编号和内容签名，按先后排列。

理由：网络抖动时同一个请求可能被发两次。后端认出编号相同、内容相同的请求，就返回上次的结果，不重复执行。只留 4 条是因为同一道题的请求是排队发的，能被重发的只有最近的那一个；留多了每次保存都要多写（V1 的这类记录占到作答文件的两成）。

### 2.3 不在这个文件里的

| 内容 | 在哪 | 理由 |
|---|---|---|
| 白板笔迹 | 独立文件，见第 3 节 | 体积大、变化频繁 |
| 题目内容和答案解析 | `bank.json` | 不复制。题库变了作答整体作废，所以不需要副本 |
| 之前各次重做的作答 | 不保存 | 只保留最后一次（D31） |
| 题型自带的非答案笔记 | 不支持 | D36 |

### 2.4 考试：`.qf-v2/exam/`（第 4 段实现）

```
.qf-v2/exam/
├── state.json     结构同 2.1，顶层多一项 exam
└── ink/           结构同第 3 节
```

```json
{ "formatVersion": 2, "exam": { "startedAt": "…", "endsAt": "…" }, "completedAt": null, "questions": { … } }
```

| 设计 | 理由 |
|---|---|
| 练习和考试各一个文件夹，内部结构相同 | 开始考试不用动练习的进度，考完原样回来（D50）。结构相同，读写的代码只有一套，只是换个文件夹 |
| 有没有 `exam/` 文件夹就是"是否在考试" | 不另存一个"当前模式"的字段，免得和文件夹对不上 |
| 只存开始和结束时刻，不存剩余时间 | 剩余时间随时在变，存了就要不停地写。结束时刻开始时算一次，之后关页面、关程序都不影响（D49） |
| 不存"已过期"标记 | 拿当前时间和 `endsAt` 一比就知道。所以不需要启动扫描或后台任务去改文件（D51） |
| `completedAt` 就是交卷时刻 | 与练习的完成是同一件事。用时 = 交卷时刻 − 开始时刻 |
| 题库或拓展被改时与练习一起清空 | 同 D27，考试不另设规则 |

### 2.5 作答文件：`.qf-v2/practice/answer-files/<题号哈希>/`（D56，待实现）

```
answer-files/<题号哈希>/
├── a1.jpg             用户插入的图片
├── area1.ink.json     答题区 area1 的笔迹，格式同第 3 节
└── …                  以后的录音等
```

`answer` 里用文件名引用，其余内容仍由拓展定，例如：

```json
{ "text": "解：设……", "images": [ { "file": "a1.jpg", "x": 40, "y": 120, "width": 300 } ], "ink": "area1.ink.json" }
```

| 设计 | 理由 |
|---|---|
| 大的内容放文件，`answer` 里只写文件名 | `state.json` 保持很小。写一笔只重写这道题的一个笔迹文件（同 D33 的教训） |
| 每道题一个文件夹 | 锁定、重做、清空都是对一个文件夹操作，后端不用到 `answer` 里找这道题用了哪些文件 |
| 提交后整个文件夹不可写 | 这些文件是答案的一部分，要和答案一起锁定。规则只看"这道题锁了没有"，后端不需要懂文件内容 |
| 答案笔迹放这里，草稿笔迹放 `ink/` | 两者规则不同：答案笔迹随答案锁定，草稿提交后还能写 |
| 答案笔迹按答题区自身的坐标记录 | 答题区移动或缩小时笔迹跟着走，始终与里面的文字、图片对齐（D55、D57） |
| 底图不在这里 | 底图是题目的一部分，每次从 `bank.json` 取（D59） |

考试的作答文件在 `.qf-v2/exam/answer-files/`；归档后在该轮目录的 `answer-files/`。

## 3. 白板笔迹：`.qf-v2/practice/ink/<内容指纹>/<题号哈希>.json`

```json
{ "ink": { … }, "inkRevision": 3, "receipts": [ … ] }
```

| 设计 | 理由 |
|---|---|
| 每道题一个文件 | 保存选项时不读写任何笔迹；保存一道题的笔迹不碰其他题（D33） |
| 有自己的版本号，与 `state.json` 的 `revision` 无关 | 画白板和改答案互不造成版本冲突 |
| 目录按内容指纹分层 | 题库或拓展一变，整层目录作废，一次清干净，也覆盖了"只有笔迹、没有作答"的情况 |
| 文件名用题号的哈希 | 题号可以是任意字符，其中有些不能做文件名 |
| 不受答案锁定影响 | 提交后仍可以写草稿（D15） |
| 重做时删除 | 重做恢复到题目的初始状态（D15） |

`ink` 的内容由白板组件决定，程序原样存取。

## 4. 历史：`.qf-v2/rounds/<轮次>/`（第 3 段实现）

每一轮是一个目录，里面是当时题库的只读副本：

```
.qf-v2/rounds/<轮次>/
├── bank.json        归档时的题库文件，原样复制
├── state.json       归档时的作答记录，结构同第 2 节
├── extensions/      归档时用到的拓展文件夹，原样复制
├── answer-files/    作答文件，结构同 2.5 节；归档后只读
└── ink/             白板笔迹，结构同第 3 节；归档后仍可写
```

| 设计 | 理由 |
|---|---|
| 一轮历史就是一个题库副本，文件格式与正在做的题库完全相同 | 回看历史可以沿用打开题库、读大纲、读题目的全部现有代码，不需要另一套显示方式，也不需要新的数据格式 |
| 复制 `bank.json` | 此后题库怎么改，这一轮看到的都是当时的题目和答案解析（D20） |
| 复制拓展 | 题目数据和能读懂它的那一版拓展放在一起，不存在"拓展改了、旧数据读不懂"的问题（D20） |
| `state.json` 原样复制 | 作答、各小题对错、分数都在里面。大纲和总分不依赖拓展就能显示，拓展万一跑不起来也不至于什么都看不到 |
| 图片、音频不复制 | 文件大，历史通常不多。`bank.json` 里的引用原样保留，回看时到题库文件夹里找，找不到显示"素材已不存在"（D20） |
| 后端拒绝对该目录的答案、提交、重做、评分写入 | 归档后答案和分数都不可变（D22）。靠"只读"这一条规则实现，不需要额外的锁定字段 |
| 笔迹仍可写 | 归档后还能做笔记（D22）。笔迹本来就是独立文件，不影响 `state.json` 不可变 |
| 先不做拓展去重 | 每轮带一份拓展，几十到几百 KB。历史不多时不值得为它增加管理逻辑，嫌大再做 |
| 放弃了静态页面方案 | 静态页面需要新写"抄页面、清理、静态显示"三块代码并先验证可行性；复制方案用的全是已有机制。代价是程序要保证旧拓展能运行（D43） |

考试归档后也是这样一轮，放在同一个 `rounds/` 下。它的 `state.json` 带着 `exam` 一项，历史列表据此标出"考试"并算出用时，不另存标记（D52）。

历史列表需要的每轮摘要（时间、得分）由后端读各轮的 `state.json` 得出，不另存索引。
