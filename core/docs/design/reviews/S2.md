## 1. 方法与口径

- Windows 11（10.0.26200），i5-13500H，16 个逻辑处理器，16,869,351,424 字节 RAM；Node v24.13.0；Chromium 156.0.8078.4 headless，1440×1000、DPR 1，与 C5a-M 相同。机器并非独占。
- 沿用 C5a-M 的 583 题合成种子：五种真实内置页面/schema/rules、富文本图片、答题区；大状态初始 5,005,393 字节，含两轮冻结历史。每档先用五型各一次答案与笔迹写入预热，正式样本不含预热。每个type/input/timing组开始前恢复同一磁盘种子（small为空、large为5,005,393B），清空仅服务端状态缓存与浏览器读题缓存，下一题加载在计时输入前完成；题库绑定、规则worker和页面/SDK缓存仍保留热态。每次保存只有一笔新输入；组内30次自动保存或6次导航会增长状态，下表另列每型实际写入范围，不声称每次字节数完全相同。
- 服务端在独立 Node 子进程，浏览器直接向它请求；没有 C5a-M 的诊断转发代理。Playwright 临时路由只替换四份宿主 JS 的内存响应，动作 HTTP 不转发、不缓冲。路由使浏览器 HTTP cache 关闭；宿主应用缓存及预取保留。不能直接把本报告与 C5a-M 的中位数之差解释为优化收益。
- 自动保存每个 size×input×type 各 30 条；切题时机每个 size×input×timing 各 30 条（五型各6条），不宣称时机子组每型30条。全部串行，不并行压测或本地回归。
- 答案终点是题型实际执行 `saved=capturedVersion` / `saved=entry.version`、即成功回复后的页面保存确认；白板终点是 saveInk 成功返回。不是浏览器驱动轮询返回时间，也不是屏幕像素绘制时间。开始点为捕获到的真实 input/change（答案）或 pointerup（白板）；描画一笔的 pointerdown→pointerup 时长不计。
- 所有五型答案 saver 的定时器均为 **250 ms**；宿主 enqueueInk 的保存定时器也是 **250 ms**。flush 会清掉计时器并立刻发起保存；未改变计时器或添加固定等待来让测试通过。只有明确要求的“等待1秒”场景使用1秒等待，并报告实际 input→click。
- 通过 iframe 的 performance.timeOrigin+performance.now 与宿主相减对齐时钟；Node 分段只计算其自身时长，不假设两进程时钟原点相同。临时探针有消息/记录开销，不声称零开销；没有精确因果分离，绝不估算扣除。长尾全部保留，P95 使用 nearest rank，中位数为中间两数平均。

## 2. 非重叠端到端阶段

| 阶段 | 答案 | 白板 |
|---|---|---|
| a | input/change→invoke(save)，含250ms防抖、快照与 answer-state 上报/排队 | pointerup→saveInk入口，含250ms防抖、笔迹合并与事件调度 |
| b | QF.save→宿主收到 save 请求，前向消息传递 | 不经过 iframe，计0（不适用） |
| c | 宿主收到save→fetch发出，包含mutate、enqueue和写队列等待 | saveInk入口→fetch发出，含快照、enqueue和队列 |
| d | fetch发出→响应头，含服务器处理和回环/浏览器调度 | 同左 |
| f | 响应头→宿主发回iframe回复，含body/JSON、onSaved缓存/大纲/状态、mutate收尾 | 响应头→saveInk返回，含同类宿主处理 |
| g | 宿主回复→iframe收到回复→页面确认 | 不经过iframe，计0（不适用） |
| h | 总耗时减上述连续区间之和，保留原始差额 | 同左 |

**e 是 d 的服务端内层分解，不与 a/b/c/d/f/g/h 重复相加**。Server-Timing 各段按既有优先级互斥；d−server.total 是观测的网络/接收前后等待差额，不能叫纯线缆延迟。f 内部 onSaved、body读取等也不再加一次。

所有表格耗时单位 ms，单元格为“中位数 / P95”。独立中位数不能相加代替总中位数。

## 3. persist 内层分解

测试进程通过 AsyncLocalStorage 给请求关联诊断ID，包装 StateStore.persist/stateBytes 与 fs 同步调用；不更换实现，不更改字节或 fsync 策略。序列化为 stateBytes 的原始执行时间，包含其既有长度检查。临时文件项为 open/write/close 的实际调用区间，fsync、rename 单列；其他是 persist 外层减上述互斥子段，含 safeDirectory/checkPath、安全路径与文件身份检查、Buffer转换、异常/finally等。只统计落在 persist 区间内的 I/O，不混入 library 读文件。目录同步、恢复日志等若无调用报告0，不估计成本。

## 6. “切题不等待保存返回”一页评估

| 路径/情形 | 已有支持、限制及必要改造 |
|---|---|
| flushPane / SDK flush | 当前SDK flush等待onFlush和全部pending Promise，题型saver.flush也等待queue/reports；宿主随后等saveInk和writes.settled。它是“持久化已确认”屏障，并非“最新输入已交付宿主”。需新增分离的捕获/入队确认语义，不能直接删除await；否则250ms未发出的输入会随iframe销毁丢失。 |
| write-queue | enqueue时快照data，捕获qid、contentVersion，真正send时用对应qid的最新revision，onSaved按qid更新缓存；能处理晚于可见题的成功回复。队列tail吞错误用于继续调度、failures另存快照；它不等于已落盘。当前snapshot只有内存且pane.closed会拒绝send。 |
| pending-answer / answer-preview | 本检出没有独立pending-answer.js；相关行为在answer-preview.js、SDK pending Set、题型saver pending与既有测试中。answerPreviews/answerStateSnapshots已按qid/stateId保护较新的本地状态，不让旧回执误确认新输入；但mutate入口读取pane.questionId，必须在切题前完成qid捕获与答案状态快照提取。 |
| save-recovery | failures包含qid/data/contentVersion，但恢复UI主要面向active pane；retry先flush当前plugin，loadSaved读取当前qid。离题后失败需要按题索引的持久可见提示/恢复入口，不能把A的失败当作B当前输入，不能不经确认清空整个pane的失败或预览。 |
| 网络错误 | 保留不可变待保存快照与requestId，在原qid重试同一请求；重复请求现有幂等仍需保留。现有queue遇TypeError只会原请求再发一次，永久失败留下内存记录。刷新会丢内存快照，若承诺跨刷新恢复必须另行审查本地持久缓存/隐私/配额，而非声称已支持。 |
| 409版本冲突 | 不能自动覆盖最新答案。按旧qid取最新状态，保留本次快照，标记冲突并让用户回到该题比较/确认重试；现有onFailed可按qid刷新状态，但当前可视化与恢复入口需扩展。 |
| 内容已变更 | contentVersion应随入队快照冻结，服务器即时拒绝仍保留。提示原题内容变化、保留旧答案/笔迹待用户复制或重答，不能在新qid上重放，也不能只修改版本后盲重试。 |
| 规则拒绝 / 状态超限 | 属不可自动重试的失败。为原qid保留输入和明确原因，回该题编辑/清理后显式重试；不得为避免阻塞而报已保存或静默丢弃。持久化失败仍依赖后端旧状态不变。 |
| 旧iframe销毁 | 现在dispose会把pending请求解析为PAGE_CLOSED，宿主destroy也停止发reply。保存若已真正进入宿主队列仍可完成，但题型自身saved/version与错误UI已不存在。必须把“已接收”“已确认”“失败待恢复”权威放到宿主按qid维护；未交付的私有输入不具备此保证，第三方拓展不能默认适用。 |
| 服务端排队 | StateStore构造器把question/overview/act等统一放入同一个SerialTransactions；单个Node进程的同步序列化/fsync也会阻塞事件循环。即使前端提前发下一题GET，它仍可能在旧写入后执行；当前loadQuestion会条件重验证，不能假定直接使用浏览器缓存就可提前可交互。需要另测实际重叠上限，不能把flush总时长全视为可节省。此限制不在本任务中修改。 |
| 大纲 / 汇总 / 完成练习 | 大纲可显示本地pending与失败，最终状态只认确认revision；汇总/完成练习、AI输入、重做等仍应等待相关写队列并检查失败，避免先完成轮次后晚到草稿写入。提交是评分/历史边界，不建议套用本次草稿/白板的后台离题方案。 |
| 关闭/切换题库 | suspendPane会flush再销毁plugin/whiteboard、清空payload与collection.states；如果后台保存未完就做这些操作，revisionFor/onSaved/read recovery可能失效。需保留独立于可见pane的写入上下文与失败快照。close时不可先置closed。跨题库不能误共享队列/资源。 |
| 刷新 / 标签页关闭 | 当前beforeunload检查pendingWrites、ink.pending、writes.hasFailures、plugin.hasUnsavedInput；仅能警告，不能保证浏览器准许完成异步请求。pagehide会销毁UI，visibilitychange尝试saveInk但不等价于成功。不得以sendBeacon/unload承诺持久成功；未确认输入仍有丢失风险，需明确产品保证后再设计。 |
| 涉及文件 | web/app.js、shared/write-queue.js、practice/save-recovery.js、practice/answer-preview.js、bridge/frame.js、bridge/api-v1.js、各题型saver、practice-lifecycle与关闭/完成/考试路径，以及相应用例；不是删一条await的局部修改。 |
| 建议测试 | A→B→C晚到成功/失败、按qid与revision隔离、未发出的250ms输入、白板与答案同时队列、旧iframe销毁、各类409/规则/大小/网络失败、重试同requestId、返回A恢复、离题后失败提示、跨库/关库/完成练习屏障、刷新警告与数据保留、第三方旧拓展维持原屏障、考试与历史不变。 |

结论：仅可考虑草稿和白板的“宿主已接收快照后并行加载下一题”，submit、完成练习及其他依赖确认的动作继续屏障。潜在节省最多为点击后还未完成保存的flush等待，但实际需扣除捕获/入队确认、前后台CPU与I/O争用及失败恢复成本。本次没有实现或实测后台保存原型，不给确定收益承诺。
