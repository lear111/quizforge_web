# K2：内容摘要缓存与同观察点 stat 复用

任务卡 K2；基于已审查合并的 K1 #55（`725a550`）。本 PR 不合并，等待审查。

## 改了什么 / 明确没改什么

将 SHA-256 元数据与正文 LRU 分离，在同步 contentIdentities 遍历中复用 walkEntries 当次取得的 stat。新增匿名只读文件数量脚本、缓存/指纹等价性测试，更新计划与性能指南。文件清单见末节。

没有改动任何响应 JSON、状态码、规则输入、版本号、回执、持久化格式、内容指纹排序/参与字段/取值、环境指纹、校验缓存键、正文缓存上限、遍历范围与 1000 项上限、写路径两次检查、任何 TTL。四份状态 / history-ai 标准答案文件未更新。没有删除逐文件 realpath / 规范路径检查，没有实现 K3/B2c、K4、fs.watch、资源延迟检查、后台保存切题、UI 提示修改或任何未批准的后续任务。

## 1. 实现与预算

`DigestCache` 只存路径（Map key）、六字段身份字符串、SHA-256 字符串，不存正文、解析值或 stat。默认最多 **8192 条 / 64 MiB 元数据记账预算**，惰性分配；超过任一预算时保留字典序较小的路径，确定性拒绝/逐出尾部。它不是 LRU：容量+1 的顺序扫描不会每遍把整棵树逐出。代价是字典序尾部不保证热点优先；跨很多题库超过预算时尾部仍可能重复哈希，但不会因扫描本身循环全量失效。`clear()` 同时清两种缓存。

每条估算为 `384 + 2 * (path.length + identity.length + hash.length)` 字节（字符串 UTF-16 加 Map/记录的保守记账）；常见路径约 0.8–1 KiB/条。8192 条容量足以容纳单次 1000 项遍历树及多个普通绑定。64 MiB 预算也可容纳一棵 1000 项、路径接近 Windows 长路径长度的树。这是**可验证的记账上限及内存估算，不是 V8 整个堆的硬上限**，不含短命对象、文件正文或探针。900 图实测保留 964 条、记账 **831226 B**；正文 LRU 保留 **962633 B**，仍最多 256 条 / 32 MiB，正文淘汰与大小/解析语义不变。未用进程总 RSS 冒充摘要缓存占用。

每次 hash 仍以新观察的 dev、ino、size、mtimeNs、ctimeNs、birthtimeNs 比较，任一变化即走原安全读取与 SHA；摘要命中仍校验本次 size 上限。readBytes 的 O_NOFOLLOW、打开后 fstat、大小检查、读取前后身份复查全部保留。没有缓存“这个目录安全”的结论。

`walkEntries` 返回的 BigInt stat 在同一同步 contentIdentities 调用内用于类型判别及 hash 身份比较；调用间没有 await，不跨请求或异步规则调用复用。hash 仍执行逐文件 canonical/realpath 检查；cache miss 的后验 stat 不能复用并且未删。bank / manifest / registry 的独立读取观察点仍独立。这里复用的是明确获批的同观察点元数据，不是原子文件系统快照，TOCTOU 边界仍与 K1 一样存在。未实施任何待审查的 realpath 合并方案。

## 3. 测量方法与规模对照

本机 Windows 11 10.0.26200、i5-13500H（16逻辑CPU）、16869351424 B RAM、Node 24.13.0。沿用 K1/S2/O1 的合成根、20/200题小状态（8354/82154 B），5个真实内置拓展；隔离动态回环端口，不读真实题目，不访问部署站/SSH。真实数据计数因日常 8787/8788 仍监听而未执行，没有自行停服务；不产生或提交真实逐文件统计。

临时工具在 git 忽略的 `C:/dev/quizforge-web-s2/.temp/k2-tools`，不加入依赖或生产开关。K2服务实际加载本 PR 的 host 模块；共享 SDK/规则 codeRoot 使用与 K1 相同且业务字节未变的 S2 检出，避免依赖/SDK与环境输入漂移。旧 Library/FileCache 来自该未改的 K1 同业务检出，新版本来自 K2；同进程同合成根分别独立缓存。AST 测试加载钩子包围 contentIdentities、fs操作和实际文件SHA，返回值/异常不变；新 hash 路径也建立文件上下文，避免漏算私有 #entry。计数是 JS fs API 调用数，不是内核调用数。

## 4. 超限时实际界面（只报告）

Chromium **156.0.8078.4**，Playwright默认桌面视口1280×720，隔离合成题库在原1张图片外增加1000张，assets目录超1000项；点击题库，浏览器可见通知 **`Request could not be completed`**，中间仍显示“加载中… / 正在校验并加载题库…”。请求 `/api/collections/bank/o1-a` 返回500，`INTERNAL_ERROR`，同样的通用message。内部walkEntries抛 `Too many files`，被现有HTTP通用错误处理隐藏。首次探针等待该内部英文原文可见而超时，后按实际HTTP通用错误重新观察并截图；没有通过放宽等待时间掩盖结果。

结论：**用户无法看出原因是该题库文件过多，也看不到当前数量与1000上限**。现有限制按每次 walkEntries 树计数，含根目录与子目录，恰达1000项可通过，第1001项拒绝；题库assets与各拓展树分别遍历，不能把“题库文件数+全部拓展文件数”直接等同于本次超限项数。建议后续单独任务给受控错误码/中文说明，报告已观察项数及上限并结束加载状态；本PR不改错误码/状态码/UI文案或计数逻辑。
