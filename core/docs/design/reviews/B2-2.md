# B2-2：提交与历史路径的写时复制

基线为已合并 B2-1（#44，6403696）。依据 [B2 设计](B2.md)，此设计已批准，直接实施；不开始 B2a。本文件同时用作本 PR 完整描述，后续结果同步更新。

## 实施计划

**目标**：200 题、5 MB v2 数据集三轮 submit clone 中位数 <50 ms；持久化输出逐字节不变。

**架构与范围**：继续使用 Node 24、显式路径复制、numericSources 保真工具和默认开启的提交冻结。保留公开 unsubmittedState、publicState、response、freezeRound 的独立副本语义；新增 StateStore 私有只读构建路径用于内部历史。共享答案、笔迹和闭合历史，复制根、轮次数组、活动轮次、collection、被改 entry/payload/question 及集合回执。仅候选成功持久化后发布缓存。

- [x] 1. 基线标准答案：从未改动 d3505cf 生成内存标准答案；比较磁盘差异，记录原因及 SHA-256。磁盘标准答案绝不更新。当前实现磁盘与内存各自 Buffer.equals。
- [x] 2. 内部历史路径：只读未提交／汇总状态、内部响应构建与汇总，保留 HTTP／规则输入深拷贝边界；recordSubmission／recordReview 按写入范围复制，去掉 act 整轮克隆。验证旧图不变、历史内容冻结、调用方修改公共返回值不影响内部。
- [x] 3. 完成路径：finish／restart／submitSaved／saveCompletionResult 复制实际写入容器；请求回执顺序、时间、UUID 消耗及失败回滚保持不变。补部分完成失败、回执替换和重放的用例。
- [ ] 4. 验证：专项测试，typecheck、build check、完整测试；不跳过／放宽旧断言。v2 三轮主测量，另测 finish／restart，对照 A1 与 B2-1；不修改 timing.js 分段和主测量动作序列。
- [ ] 5. 完整记录、计划进度、独立 PR 与三个 CI job 结果，PR 描述与本文件同步；不自行合并。B2a 在此 PR 合并后才开始，仅诊断并等待审查。

## 不改什么

不改变响应 JSON、状态码、规则输入、版本号、回执内容和持久化格式；不更新磁盘标准答案，不改变 unsubmittedState/publicState 等公开导出语义，不优化环境解析、拆历史文件或瘦身回执，不部署、不连接业务远程服务器、不操作真实题库。

## 验证重点

1. 活动轮次与当前题分离；完成后修改当前答案／笔迹不影响历史。
2. 规则拒绝、写盘失败、同 requestId 重放保留旧图及字节；submitSaved 的部分成功仍按原语义保留。
3. 公开历史与响应可由调用方修改，内部私有共享视图不能经公开接口返回。
4. 数字元数据、字段顺序、UUID／时间／stampKey 行为与标准答案相同。
5. 磁盘和内存模式都默认冻结，并有各自基线字节比较。

复制边界：候选根及实际写入的祖先为新对象，旧图默认深冻结；提交持久化与配额成功后仍由 remember 冻结并发布。规则输入的 state 经 publicState 或独立 result 副本构建；新增私有路径不导出，借用的 draft 不进入 HTTP 返回值或规则输入。公开 response 始终 borrowDraft=false，公开 freezeRound 仍复制笔迹、答案和汇总状态。unsubmittedState/publicState/summaryStates 未改变其公开实现。#summarizeRound 沿用 summarize 的计算与字段顺序，只让内部 states 引用不可变 payload.state；公开 summarize 不改，默认冻结和标准答案检查这条边界。

一次专项测试发现 response 原有 project 输入直接引用了持久 state.result（在修改提交后的笔迹时出现）。现改为 cloneJson(result) 后交给规则；规则收到的数据值与原来相同。测试同时检查 projectBatch/scoreBatch 的 questions[].state 子树，不只检查最外层对象。另一轮新测试首次未 await 事务包装的 saveCompletionResult，导致断言早于提交；修正测试为 await，未更改事务语义。

## 标准答案与兼容性

原磁盘标准答案保持 **73,984 字节**，SHA-256 **07849dbea421df2de8d9034522151018295a2615bafd21b2702be94b3889ef50**，本 PR 没有修改。原固定动作序列不变：draft、whiteboard、首次／后续 submit、整题及分目标 review、retry、bindAiTask/confirmAi、finish、restart、规则拒绝、requestId 重放、写盘失败后重试；对每个动作的旧图都保留字节快照检查。未删除字段、排序、擦除时间或重编码标准答案来迁就实现。

内存标准答案由未改动 **d3505cf3642bd90cffb0a9738dd3c30288329674** 的真实 Library/RuleEngine/StateStore 运行同一生成脚本得到：

```powershell
node core/scripts/dev/state-golden-scenario.mjs C:\dev\quizforge-web-b2-golden-base\core .temp/b2/golden-memory-d3505cf.json memory
Copy-Item -LiteralPath .temp/b2/golden-memory-d3505cf.json -Destination core/test/fixtures/state-golden-memory-d3505cf.json
```

内存文件 **73,950 字节**，SHA-256 **698b1e5fb38c6a28e09b588da4b761b86f777175c548902913fed8b2baac97ac**。固定 Date/UUID/randomBytes/stampKey 的方法和场景脚本没有变。两种模式不能共用一个最终文件，原因可在基线复现，并非本次重构引起：replaceFile 每次为 .write-${randomUUID()}.tmp 消耗一个 UUID，内存模式不写盘；新轮次 ID 分别为尾号 008 和 003。内存 finish 按既有设计返回 historyId=null，磁盘返回轮次 ID。因此共有 9 个标量位置不同：historyRounds/1/id、其 summary/roundId、finishReceipts/0/request 的 roundId/summaryVersion、其 response 的 roundId/historyId/summaryVersion、restartReceipts/0/request 的 roundId/summaryVersion。签名变化由既有 roundId／summary 输入变化产生。没有额外题目、答案或笔迹差异。现在两种模式分别用 Buffer.equals 比较未改动基线，CI 深度 1 不需要基线代码。

专项验证还明确修改当前答案和笔迹后活动／完成轮次不变，并修改公开 history、response、publicState、unsubmittedState、freezeRound 的返回值后检查内部状态不变。已有部分 submitSaved 规则失败后保留已提交题、继续原 intent 的用例继续保留。没有关闭冻结、放宽断言、延长超时或增加测试重试。
