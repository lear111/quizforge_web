## 2. submit 为什么比 draft 多出大批克隆

不能把 2478 对 1146 ms 简化为“submit 有两次 cloneJson(persisted)”：S:388 **每次 act 只有一次整份 P 克隆**。submit 另外进入 recordSubmission：首次通过 S:226 的 200 次 unsubmittedState（S:29 深克隆整题，含回执和笔迹），freezeRound → response 逐题再克隆 draft；后续提交通过 unsubmittedHistoryStates:219–221 克隆其余未提交题，recordSubmission:234 再克隆对应 draft。H:summarize 又复制各 payload.state。新增活动轮次还使后续 S:388 克隆的 P 更大；A1 测量顺序是 draft → whiteboard → submit。

只读源码之外，使用现存 A1 v2 种子（5,002,406 字节、200 题、两轮历史）的**临时副本**做了调用追踪：虚拟模块加载钩子只在内存替换 cloneJson 的诊断包装，记录原 stringify 结果的 UTF-8 字节数和调用栈；没有改仓库源码或计时定义，也没有计入下表以外的性能结论。依次执行 q001 draft、whiteboard、submit，再 q002 submit，结束关闭规则进程并删除本次临时副本；种子哈希前后相同。诊断所用 T2 检出的 S／H／J 与本分支基线文件逐字节相同。

| 动作 | cloneJson 次数 | 输入字节合计 | 整份 P 克隆次数／字节 | 额外大块复制 |
|---|---:|---:|---|---|
| q001 draft | 8 | 5,102,754 | 1 / 5,002,406 | 当前整题 52,961 字节 |
| q001 whiteboard | 8 | 5,120,686 | 1 / 5,026,289 | 当前整题 76,844 字节 |

## 3. 写时复制的具体边界

采用显式路径复制，不增加代理式草稿库。保留边界 cloneJson，比全局换克隆函数更容易审计数字语义及字段顺序。

1. 普通动作只新建 P、questions 映射、Q；复制 Q.receipts 数组后 push／shift，旧回执对象共享。review 分目标时另复制 aiTargetGenerations／aiTaskIds 等实际改动的映射。输入答案、规则输出、请求回执快照和对外返回值继续独立复制，调用方修改返回值不得污染缓存或历史。
2. 仅修改历史时复制 historyRounds 数组及被修改 R；复制 R.collection，按写入范围复制 R.questions 数组、被触及 entry／payload／question 容器。未触及轮次、页面源码、题目数据、答案、笔迹均可共享。修改 upgradedCompletion.completionVersions 或集合回执 response 时，复制对应容器与回执项；不得只复制根后改深层字段。
3. submit 的全题历史遍历使用**内部只读视图**：筛选状态字段、转换未提交状态时新建浅层容器，不携带／复制无用的 receipts；冻结笔迹与答案可引用不可变子树。summarize 对内部只读 payload.state 建新 states 映射；保留计数算法、字段顺序、调用顺序和历史 JSON 内容。freezeRound 的外部／升级调用仍须具有独立快照语义；只对 StateStore 已拥有的不可变图启用内部共享快路径，不能让未受约束的可变实参偷偷进入历史。
4. `publicState`／`unsubmittedState`／`response` 区分内部只读构建和跨边界独立副本：HTTP 返回、规则引擎输入、公共历史读出、可被调用方修改的对象仍防御性深拷贝。新增私有视图路径，不把现有导出函数悄悄改成借用可变对象。共享快路径不返回给前端或第三方规则。
5. StateStore 的 load 整图冻结，remember 在成功写盘／配额检查后对新容器增量冻结，已冻结节点停止下探。没有关闭入口，考试和临时内存模式相同；旧图不能原地修改。测试持有旧图及 jsonBytes 快照，成功／失败均逐字节比较，并验证共享与替换容器身份。保留 SerialTransactions 的串行、重入和版本冲突语义。

## 4. 写盘失败与缓存替换

保留 S:150 的顺序：构造独立候选 → stateBytes／大小与内存配额检查 → persist → replaceFile（临时文件写完、fsync、原子 rename）成功 → remember 替换缓存。提交前不把候选挂入 cache，失败直接丢弃候选，旧图和原磁盘字节保持不变；不新增 rename 重试或清空原文件。内存模式在配额检查成功后才换缓存，失败继续保留原图。

## 5. numericSources：普通浅拷贝不正确

J:6 的 WeakMap 以**父容器身份**关联字段数字字面量；J:105 的 stringifyJson 和 J:132 的 integralField 依赖它。共享未修改的子对象会保留原身份和元数据；`{...old}`／数组 slice 创建新父容器则丢失该父容器的元数据。使用现行 J 的无依赖探针得到：

```text
原对象／cloneJson：{"n":1.0,"big":9223372036854775807,"child":{"n":1.0}}
普通对象展开：     {"n":1,"big":9223372036854776000,"child":{"n":1.0}}
integralField(n)： 原对象 false，普通展开 true；共享 child 的 1.0 仍保留
```

因此实现需在 J 内提供窄用途、保留元数据的浅复制／字段投影辅助函数：按原有键顺序定义自有属性（含 __proto__ 安全处理），为新父容器复制数字元数据 Map；不暴露 WeakMap，不修改原 Map。共享子树不递归复制；新写入字段按现行 Object.is 原值校验与原深克隆路径保持一致。数组发生索引移动时必须按新索引重建数字元数据，不能把旧索引 Map 机械搬过去；回执／轮次数组当前是对象元素，也要明确测试这个前提。不使用 JSON.parse／JSON.stringify／structuredClone 代替保真工具。

实施复核补充：新父容器的数字元数据按旧 cloneJson 的数字序列化／解析结果刷新，不能机械复制已经失效的 literal。例如旧 n=1.0 改为 2 后复制，再将新副本改回 1，旧深克隆应得到整数 1，不能复活 1.0；新计算的 1e21 也必须获得与 cloneJson 一致的节点类型。新增回归在初版实现 2e05a3c 的虚拟加载副本上稳定失败（1.0/2.0 对 1/2），修订后通过，未改旧解析／序列化规则。

依据及回归：现有 [foundation.test.mjs](../../../server/host/platform/foundation.test.mjs) 的 numeric node kinds／large integer bytes、指纹、原型安全用例全部保留；新增父容器复制、共享子树、数组索引、1 vs 1.0、指数、大整数、浮点 -0.0、整数 -0、修改数值及相同数值覆盖用例，与 cloneJson 的最终字节和 integralField／fingerprint 对照。整数 -0 在既有深克隆中归一为 0，须核对该差异，不能仅搬元数据后宣称完全等价。
