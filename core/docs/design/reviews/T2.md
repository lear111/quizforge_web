## 调查 a：问号产生于哪一步

本机未改动的生产 C# 源码与一个临时同程序集入口共同编译，入口只设置进程输出编码后调用真实 `Options.Parse` / `Program.Run(--layout)`。Node 以 Buffer 接收 stdout，在任何字符串解码前检查字节：

| 输出路径 | 编码 | 原始字节证据 | Node 按 UTF-8 解码 |
| --- | --- | --- | --- |
| 真实 Program.Run 的 layout JSON，路径包含“应用 中文” | 437 | 中文位置已是 `3f3f203f3f`，共 8 个 `3f`（两个路径字段） | `?? ??` |
| 相同调用及路径 | 65001 | 中文是合法 UTF-8；没有 `3f` 替换 | 正确保留原路径 |
| Windows PowerShell 5.1 Write-Host 中文 | 437 | `3f3f0a` | `??` |
| 相同 PowerShell 调用 | 65001 | `e4b8ade696870a` | `中文` |

最小复现命令（在 Node 中执行，直接打印子进程原始字节；不更改系统语言／注册表／机器代码页）：

```powershell
node --input-type=module -e "import {execFileSync} from 'node:child_process'; const ps='[Console]::OutputEncoding=[Text.Encoding]::GetEncoding(437); Write-Output ([string][char]0x4E2D+[char]0x6587)'; const bytes=execFileSync('powershell.exe',['-NoProfile','-NonInteractive','-EncodedCommand',Buffer.from(ps,'utf16le').toString('base64')],{windowsHide:true}); console.log(bytes.toString('hex'));"
```

执行结果的中文位置是 `3f3f`。将命令中的 437 换为 65001 后，中文位置是 `e4b8ade69687`。EncodedCommand 使用 UTF-16LE 和字符码点生成字符串，排除了脚本文件读写编码和命令源文本编码问题。两次都不通过 tee。

结论边界：已定位到**子进程输出编码丢失**，不是 Node UTF-8 解码把正确中文字节替换成问号；也不是测试把中文比较成了错误的字面值。仍需下述 CI 对照明确 Git Bash／tee 是否影响默认编码。
