# V2：暖状态题库概览后端分段

接续 [#102 的测量要求](https://github.com/lear111/quizforge_web/pull/102#issuecomment-6860460692)。在 `GET /api/v2/banks/:bankId/overview` 成功响应加 `Server-Timing`，与写接口共用已有 `V2Server({ timings })` 开关；写接口分段原样保留。计时区分题库目录与树检查、读取及解析题库 JSON、全量拓展扫描及本题库使用的题型解析、SDK 摘要、两个顶层指纹、作答文件、笔迹索引、实际读取的笔迹正文、响应组装与序列化。保留这组计时边界供后续接入历史。只增加诊断，不优化缓存或文件检查，不改变 API JSON、状态码、作答及存储、浏览器切换或 iframe。

Windows 10.0.26200 / i5-13500H / Node 24.13.0，独立临时合成根与随机回环端口，沿用 #102 的 A、B（各 3 道单选，首题有一张图）；另测 A 已保存答案及首题笔迹。同一进程先打开 A/B、每场景再预热 6 次，交替 B→A；按 ABBA 顺序交错开关，每个场景开启及关闭各 30 次。所有响应须成功、无未锁定答案，且同场景原始响应正文逐字节一致。服务端从概览路由分发到 JSON 序列化完成，不含路由验证、套接字写出或客户端 JSON 解析；客户端从发请求至收响应头或解析完成。不同分段的分位数不可相加。

第一轮客户端全响应（启用 / 关闭计时）：无记录 148.0 / 392.3 对 165.0 / 305.0 ms（各组中位数 / P95）；有记录 151.3 / 325.0 对 137.3 / 317.5 ms。逐请求“到响应头减后端总耗时”的中位数 4.4 / 3.5 ms（两场景）。分段和与总耗时最大差值 0.003 ms，来自三位小数舍入。并行检查期间复测时机器波动较大：后端总中位数 219.9 / 307.5 ms；客户端开/关中位数分别 230.6 / 273.8、330.7 / 348.5 ms。开关差值不稳定，不能作为插桩开销估计。#102 浏览器的约 80 ms 与这里不是同一次采样，不直接比较；只测合成题库，未测真实数据或其他机器。

**结论：未到 20 ms。** 两轮最大的三段都是拓展扫描、所用题型解析和 SDK 摘要；复测按每个请求合计这三段的中位数为 132.2 / 155.2 ms。独立的五次暖态观测中，每次都扫描一次整个拓展目录，检查并解析三份 manifest（包括两份未使用的），实际重新打开 manifest 正文 0 次：使用缓存的原始字节，仍检查文件身份并解析。每次只解析一个实际用到的题型，并重新遍历它声明的一个 SDK 以计算摘要。两个顶层指纹和响应序列化占用较小；有笔迹时还需读取首题笔迹，不能与索引检查混为一项。以上数字用于下一步决策，本 PR 不改变检查策略。

复现：`node core/scripts/dev/measure-v2-overview.mjs`；自动清理临时数据，不读真实题库，不用日常端口。回归：`core/test/v2/timing.test.mjs` 新增一个用例，验证分段互斥与合计、开关、其他 GET 不带该头、开关两组响应正文逐字节一致；原有写诊断用例保留。

验证：本机 UI 类型检查、构建核对、计时用例 2/2 通过；本机 V2 定向检查 89/90，D19 私有记录用例在建立 1,005 个文件后发出概览请求时收到 `ECONNRESET`，未改动的 `48a9aec` 单独运行该用例也得到同一错误。本机并行全量/性能检查曾出现旧版规则进程超时；以 [代码头 `5f6a8c1` 的 CI](https://github.com/lear111/quizforge_web/actions/runs/43480043218) 为准：Windows Checks、Ubuntu Checks、Ubuntu Performance 均通过，无失败用例。
