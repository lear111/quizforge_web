|---|---:|---:|---:|---:|
| small-no-ink | 2.693 / 3.341 | 1.391 / 1.749 | 1.94× | 2.531 / 3.133 |
| small-with-ink | 3.660 / 6.407 | 1.893 / 3.488 | 1.93× | 4.242 / 6.166 |
| large-with-ink | 47.704 / 116.366 | 35.543 / 62.839 | 1.34× | 14.733 / 25.337 |

`replaceFile` 原样执行：Buffer 复制、受检路径、临时文件写入、**一次文件 fsync**、关闭、rename；无目录 fsync。目录复制使用 `fs.cpSync`，bank 使用 `copyFileSync`，未额外 fsync。逻辑字节是目标普通文件大小之和，非物理磁盘写放大/元数据；没有把临时文件与 rename 再算一份。无笔迹时仍复制空 ink 目录，因此不是 0 ms。复制内容及总字节在计时外核对，清理也在计时外。

## 编码字节兼容性与判断

三个主数据集两种编码器输出**逐字节相同**，但不能推导任意输入等价。额外数字探针（同一个 `parseJson` 对象）：

| 字段 | 原始 JSON | jsonBytes | 原生 UTF-8 编码 |
|---|---|---|---|
| float | `1.0` | `1.0` | `1` |
| exponent | `1e7` | `1.0E7` | `10000000` |
| integer | `9007199254740993` | `9007199254740993` | `9007199254740992` |
| zero | `-0.0` | `-0.0` | `0` |

原因：现有编码器使用 numericSources 保留数字节点种类，整数源文本还避免精度损失；并非保留所有原始词法，例如指数会标准化。原生编码丢失这些信息。**不替换编码器。** 此前“约 7 倍”来自不同结构，不能套用于主要为长文本、且笔迹已拆文件的状态；本次比值为 1.34–1.94×。

主要瓶颈是**多文件目录复制**：无笔迹时拓展复制最长；有笔迹时 100 份笔迹复制最长，其次为拓展复制或大状态编码。更大笔迹场景比小笔迹场景复制中位数更低，不代表大文件更快；这是不同时间段样本与系统缓存/后台活动的不确定性，不能据此建立线性模型。

**建议：目前没有证据要求把编码器优化作为 J 的前置条件。** 先按已确认设计实施；若后续实际归档仍显慢，最小方向是落实规范已有的“移入笔迹”（本次为满足复制测量使用 copy，未测试 rename 的收益），并测量其失败恢复；不要引入压缩、缓存、拓展去重或改 JSON 格式。本 PR 仅提出建议，不实施。
