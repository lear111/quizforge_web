# QuizForge Extension API 1.5

This document specifies the browser SDK, synchronous rule hooks, HTTP routes and persistence guarantees for QuizForge Web. The host manages lifecycle, permissions and storage; extensions own question data, projection and grading.

Paths are relative to the product root. See [development and architecture](../guides/CORE_SOURCE.md) for source organization, [extension development](EXTENSIONS.md) for packages/examples, and [compatibility](COMPATIBILITY.md) for updates and explicit migrations. The bank format remains version 1.

## Version compatibility

See [API v1 and update policy](COMPATIBILITY.md). Current support is Extension API 1.0–1.5 (`{major:1,minor:5}`) and bank format `1`, separate from application, extension and public SDK versions. Only API v1 is implemented; unsupported future versions require actual host runtime support and are rejected today.

- Manifest optional `requiresApi:{major:1,minMinor:0,capabilities?:string[]}`. Absence means v1.0; an explicit object requires integer major/minMinor (at least 1/0), permits only those three fields and unique nonempty capability strings. Supported capabilities: `practice`, `editor`, `editor-drafts`, `score`, `manual-review`, `ai-grading`, `resources`, `richtext`, `navigation`, `lifecycle`, plus `outline-items` with `minMinor` at least 1, `answer-state` with `minMinor` at least 3, `appearance` with `minMinor` at least 4, and optional `answer-areas` with `minMinor` at least 5. A supported protocol capability never grants a write permission; ordinary context.capabilities and SDK dependencies still apply.
- Bank/example top-level `formatVersion` is optional; absence means 1 without rewriting the file. Explicit values must be integer 1. This field is independent of extension-private data and rich-document versions. Unsupported API/bank declarations are refused before extension rules run.
- Bank/example root `features` is optional and accepts only boolean `editing`, `whiteboard`, `history` and `exam`; all four default to true and only an explicit false disables the feature, and question-level overrides are rejected. Collection metadata exposes the normalized object. These collection permissions do not change the Extension API version or type bindings. Editing false denies authoring; whiteboard false denies the whiteboard without disabling answer updates. History false disables ALL practice persistence, including answers, grades, ink, finish status/history, practice-uploaded resources and AI tasks; state belongs only to the current browser page session and cannot be restored after page refresh or browser-tab closure. Closing/reopening a collection tab within that page can retain temporary state. Editing true still writes authored question/sample documents and editing images to source. New example banks default all four to true; existing explicit false example policies remain readable. See [collection features](QUESTION_BANK_FORMAT.md#整库功能开关).
- Current practice/editor page assets carry `apiVersion:{major:1,minor:5}`. Browser `QF.api` exposes the selected bridge version and capabilities (legacy missing/1.0 pages retain their 1.0 metadata); current rule-environment `QF.api` exposes 1.5 without browser methods. Frozen history retains each page's selected version; legacy pages/requests without one default to v1.0. Incompatible declared history pages and rule requests are refused rather than run under another version.
- API 1.4 adds the read-only `appearance` capability: `QF.ui.appearance` (`{theme,transparency}`, frozen), `QF.ui.onAppearanceChange(callback)` returning an unsubscribe function, and `data-qf-theme` / `--qf-transparency` on the page `<html>` from the first paint. `transparency` (0–0.7) is the shell panel transparency and is forced to 0 for the default look, draft mode and the phone layout (≤600px). The host never restyles extension cards. Manifests that depend on it declare `minMinor:4` with `appearance`. Pages of API 1.3 and older, including frozen history, get none of this. See the skill reference `extension-api.md` (宿主外观).
- API 1.3 adds optional `answer-state` and `QF.page.reportAnswerState({status,targetId?})`: one unanswered/draft patch, optional stable child ID within the bound parent; omission targets the parent. Other children are retained, initial missing states default unanswered, clearing requires explicit unanswered. Returns `{ok:true,data:{status:"reported",stateId}}`; the corresponding draft answer save carries top-level `answerStateId`. The host snapshots feedback and sends HTTP `data.answerState:{status,outlineStates}` with the same answer, validated and persisted atomically. Reporting alone never confirms persistence or changes scores/revisions; older saves cannot clear newer feedback. Unknown/expired IDs are rejected, snapshots are bounded to 256 per pane. New declared types do not run getScore for unsubmitted saves/reloads; summary may still request maxima but ignores unsubmitted getScore outlineStates. Submitted/history/editor/handed-in exam views reject reports. Legacy 1.0–1.2 types retain their polling contract. See [child outline contract](SUBQUESTION_OUTLINE.md).
- Existing files, package fingerprints and state identities are unchanged by defaulting old declarations. Add declarations only to new banks/packages; never rewrite a released package merely to add compatibility metadata. Exact extension/SDK bindings and immutable snapshots remain authoritative.
- API 1.5 adds opt-in `answer-areas` (`minMinor:5`): only declaring pages receive frozen `QF.answerAreas`, currently component version 1.4.1, formatVersion 1, with `mount(container,{id,targetId?,label?,width?,height?,allowText?,sharedInk?,onChange})`. With sharedInk:true it defines a visible crop rectangle over the host single draft canvas, sharing its brush, eraser, selection and undo stack. Guidance stays outside the crop; no placeholder is used. Optional `allowText:true` provides one plain text box with an ink overlay; both remain visible in practice. The answer schema must allow optional `text:string` (up to 20000 characters). Extensions save tagged `type:"qf-answer-area"` documents through existing answer/state methods. A region with ink produces one host-generated PNG containing text and ink; the host removes incoming snapshots and adds immutable `snapshot:{type:"image",attrs:{assetId}}`. `prepareAiGrading` sends only that image for the region, or a text block for a text-only region, including completion and exam hand-in. Opt-in images support double-click selection, dragging to move, proportional corner resizing and confirmed deletion; floating controls stay outside grading output. Height belongs to question data and is configured in the extension's editor through the existing editor contract. No new HTTP scoring-material bypass is introduced. Pending submissions remain pending, and frozen history retains component source/style and images. Frozen 1.0.0/1.1.0/1.2.0/1.3.0/1.3.1 components and old ink documents remain supported; older non-opting-in extensions/pages are unchanged. See [answer areas](ANSWER_AREAS.md).
- Normal launch no longer enables automatic short-answer migration. The explicit root launcher `-UpgradeShortAnswer` enables the known upgrade; same-root running/starting services cause that option to fail clearly. No software updater, embedded Hub service, general migration engine or v2 runtime is included.


## Extension packages and rules

Declared package paths are relative to their extension leaf; bank assets are relative to their bank directory. A physical group has no package identity. The host owns `.state/` and controlled editor transactions.

- `question-banks/<folder>/bank.json` or `question-banks/<group>/<folder>/bank.json`: `{formatVersion?:1,id,title,description?,extension?:{path},questions:[{id,title,extension?:{path},outline?,data}]}`. Root extension is a default; per-question references override it, and every question needs a valid effective reference. Question `data` is owned by its extension. Optional `outline` is host-owned: exactly `{level:'question',label}` or `{level:'parts',items:[{id,label}]}` (1–100 children). It selects a parent OR its children, never both; child entries inherit their parent's type. Explicit metadata bypasses that question's legacy outline-generation rule. See [question-bank format](QUESTION_BANK_FORMAT.md). Directory banks carry independent images in `assets/`; resource references use content IDs, not filesystem paths or base64 documents.
- `extensions/<group>/<folder>/manifest.json`: `{id,version,name,description,entry,script,style,rules,questionSchema,answerSchema,examples,dependencies?,requiresRichText?,requiresApi?,assets?}`. All declared file paths are relative to that folder; new rich-text requirements use `requiresRichText`; legacy dependencies are exact public SDK `{id,version}` references. Optional `assets` is a bounded list of local image/font paths inlined into static HTML/CSS. The same declarations work for every extension; media bytes participate in package fingerprints. Dynamic uploaded rich-text images continue to use `QF.resources`.
- `examples` file: same question-bank shape (ID `examples`) using only this independent extension. Backend catalog exposes it as an example collection; answers/ink are separate from real banks, subject to features. When editing is enabled, controlled authoring writes the sample questions and adjacent images back to this file; manifest/rules/Schema/page/SDK version code is not editable through sample authoring. Example JSON and only-sample raster uploads do not participate in the installed extension code fingerprint; explicitly declared manifest.assets are included in content fingerprints. Incomplete actions explicitly fail; labeled local UI demonstrations are not real saves or grades.
- `.state/`: Host-owned current practice, per-question whiteboard, collection-round history with frozen practice assets, bounded request receipts, and edit recovery journal. Independent subdirectories preserve editor drafts, immutable resources and pinned public SDK versions. Completed rounds are immutable; active rounds update with submissions and confirmed reviews. Current state and history share the 32 MiB collection-file limit; reaching it rejects new writes without silently pruning old history.
- Optional `extensions/<folder>/editor.json`: `{entry,script,style}` for an extension-owned raw-question editor; these editor assets do not alter the immutable practice package fingerprint.
- Practice/example views receive only extension `project(data, {submitted,result})` output; history receives its frozen public projections, including unsubmitted questions. The explicit editor endpoint returns raw question data, including answer keys, for authoring through the same authenticated API.
- Rules script calls `QF.defineType({project,validateQuestion?,validateAnswer?,grade,getScore?,review?})`. `grade(data,answer)` returns a numeric `{score,maxScore,correct,feedback}` result, optionally marked `gradingStatus:"graded"`, or a pending `{gradingStatus:"pending",score:null,maxScore,correct:null,feedback}` result. `review(data,answer,review)` must return a graded numeric result; each extension validates its own score limits and steps. Optional `getScore(data,state)` returns `{score,maxScore,outlineStates?:[{id,status}]}` with finite nonnegative maxScore, null score only for pending submissions, and otherwise finite score; the host does not constrain earned score to `[0,maxScore]`; state includes status/answer/result/revision and a submitted boolean. Extensions own grading and score output; The host aggregates only graded earned scores, counts pending submissions separately, and counts unsubmitted questions as zero while retaining their maximum. API 1.2 adds only optional outlineStates through the existing score capability: up to 100 unique plain IDs with unanswered/draft/correct/incorrect status. Before submission only unanswered (empty) or draft (saved, unsubmitted input) is allowed; submitted children cannot use draft. New answer-state types push input progress and persist answerState snapshots; getScore supplies only scoring and post-submit child statuses. Unsubmitted legacy child input detection remains through getScore for compatibility. Ordinary parent buttons use the saved answerState status when present, otherwise state.status. Practice and exam share these display states; draft never contributes earned score or exposes correctness. The host derives ordinary parent colors from the submitted result; child colors come from extension-provided outlineStates. Pending still retains score:null and its grading-progress/error message, rather than a fabricated scored zero. Host matches child IDs within each parent, never infers all children from parent correctness, and never adds child scores. Details are cached by content/answer/result (512 parents / 2 MiB LRU, excludes ink/revision), exposed in public state/summary rows, and frozen in history; reading history does not rerun rules. The runner adapts existing single-choice 1.0.0 from submitted results or unsubmitted public projection maxScore. Schema validation uses AJV in the rules runner. Rules have JSON input/output and run synchronously in a deadline-limited child process with restricted filesystem permissions; local administrator-supplied plugins only in v1 (not a full hostile-code OS sandbox).


## HTTP contract

Mixed binding details: a bank using any question-level reference (or omitting the root default) has `extension:null` and an `extensions` array; each question identifies its effective extension. UUID bank state uses `bank:<routeId>:mixed`, including root-default banks; legacy string-ID root-default banks retain `bank:<id>:<extensionId>:<version>`. Content changes invalidate affected current answers with backups, never frozen history. Bindings distinguish physical paths, while bounded rule batches share identical ID/version/runtime fingerprints and restore original question order. Mixed history uses immutable `pages[pageKey]` and per-question keys including optional physical path, preserving old snapshots without that field. Cache capacities remain unchanged.

- `GET /api/catalog` -> `{banks:[{id,title,description,questionCount,extension:{id,version},error?}],extensions:[{id,version,name,description,questionCount,error?}]}`. Bad entries are reported separately without breaking good entries. Directory rescanned on refresh.
- `GET /api/collections/{kind}/{id}` where kind is `bank` or `extension` and id is the catalog route ID -> `{id,title,kind,extension:{id,version,name,path?,pageId?}|null,extensions:[{id,version,name,path?,pageId?}],questions:[{id,title,type:{id,version,name,path?,pageId?},outlineLabel?:string,outlineItems?:[{id,label}]}],states:{[questionId]:{status,answer,result,revision,outlineStates?:[{id,status}]}},error?}`. The optional parent label and child items are mutually exclusive. Matrix groups adjacent equal parent type ID/version pairs without changing question order, and expands child items in place. Mixed banks resolve each question's extension; legacy root-level bindings remain compatible.
- `GET /api/collections/{kind}/{id}/questions/{qid}` -> `{extension:{id,version,name},stamp:{revision,contentVersion,packageVersion},question:{id,title,data},state:{status,answer,result,revision,answerState?:{status,outlineStates},outlineStates?:[{id,status}]},capabilities:{canReview},draft:{schemaVersion:1,viewport:{x,y,zoom},strokes:[],paper:{color,pattern},layout?:{width,padding,top}}}`. `question.data` is public projection. Missing whiteboard draft may be null. status is `unanswered`, `draft`, or `submitted`; result is null until submit and can then be pending or graded. canReview requires a matching submitted manual result in the current active round and is false after completion.
- A question GET may include `X-QuizForge-Question-Stamp` containing the JSON stamp from its cached payload. If all three fields still match, the response is `{unchanged:true,stamp}` without projection; otherwise it is the full current question response. Authentication, content checks and session isolation still apply. Clients without this header receive the full response.
- `GET /api/collections/{kind}/{id}/questions/{qid}/stamp` -> `{revision,contentVersion,packageVersion}`. Warm reads verify content/state without Node projection. Opaque keyed versions reset on server restart. Browser uses conditional question GETs before reusing cached public payloads; packageVersion shares page assets across questions.
- `GET /api/extensions/{id}/{version}/page` -> `{apiVersion:{major:1,minor:5},html,script,style,dependencies?:[{id,version}]}`. Backend reads only manifest-declared page assets and supported SDK references. It does not expose rule files, schemas, or raw bank JSON through static hosting.
- `POST /api/collections/{kind}/{id}/questions/{qid}/actions` body `{requestId,revision,contentVersion?,action,data}`; action `draft` (`data.answer`), `submit` (`data.answer`), `review` (`data.review:{score,feedback?}`), `retry` (`data:{}`), `whiteboard` (`data.draft`). Successful reply is the same full question response as GET. Revision guards all writes, including reviews; review also requires an eligible active-round submission and atomically updates current state and the same history round. Browser captures the displayed question's contentVersion when enqueueing a write; a mismatch returns `409 CONTENT_CONFLICT` before grading or persistence. Failed retries retain that version until explicit server reload remounts the question. Persist bounded request receipts so identical replay returns its existing result, including after server restart, and reused ID with different request fails. Revision conflict HTTP 409.
- `GET /api/health` -> `{ok:true}`.
- `GET/PUT /api/settings/network` are local management endpoints, requiring the main loopback listener, loopback peer and loopback Host plus write-origin validation. Response `{canManage,enabled,publicEnabled,publicUrl,port,passwordConfigured,urls,ipv6Supported,publicIpv6Urls,error?}`; PUT `{enabled,publicEnabled?,publicUrl?,port,password?}`. Empty/omitted password retains the current verifier; initial enable requires at least 8 characters. LAN and public access share one password-protected connection listener and the same library/state store. That listener uses the Node IPv4/IPv6 dual stack when IPv6 is available and falls back to IPv4 otherwise; the administrator listener stays loopback-only. IPv6 URL literals require brackets, Host/Origin comparison normalizes equivalent literals without resolving domains, and scoped/link-local addresses are excluded from browser address lists. LAN accepts private/unique-local peers and global IPv6 peers on an actual local interface subnet (prefix at least /64); public access requires the configured authority. `publicIpv6Urls` lists detected global IPv6 candidates, not proof of reachability or automatic exposure. `.state/network-settings.json` stores configuration and a salted PBKDF2 verifier; never plaintext passwords. Changing modes/address/port/password revokes remote sessions. Forwarded requests cannot use the loopback administrator listener.
- LAN HTTPS: PUT also accepts `httpsEnabled?` (requires `enabled`) and `httpsPort?` (1024..65535, different from the local and connection ports, default connection port + 1); responses add `https:{enabled,configured,port,urls,certificateUrls,fingerprint?,rootSubject?,rootValidTo?,names?,serverValidTo?,serverNames?,certificateQr?,urlQr?}`. The HTTPS listener is always remote: it shares the LAN switch, password, peer, Host (plus the certificate host names, default port 443) and `https:` Origin checks, and never grants management. `GET /quizforge-lan-ca.crt` returns only the public root certificate (DER, `application/x-x509-ca-cert`, no password) while HTTPS runs, and 404 otherwise. `POST /api/settings/network/https/regenerate` (local management, JSON body `{}`) replaces the root and server certificates; installed roots must be reinstalled. Keys stay in `.state/lan-https/` and are never served.
- `POST /api/auth/login` accepts `{password}` and returns `{token}`. LAN API calls use the returned short-lived random token through `X-QuizForge-Token`; the browser stores only this session token. Login is origin-checked and rate-limited. Existing command-line token authentication remains compatible. Settings do not edit the OS firewall or add per-user practice state.
- `GET /api/collections/{kind}/{id}/summary` -> `{score,maxScore,submittedCount,gradedCount,pendingCount,questionCount,finished,status,roundId,summaryVersion,questions:[{id,score,maxScore,submitted,status,gradingStatus,outlineStates?:[{id,status}]}]}`. Pending row score is null; aggregate score includes graded results only. `POST .../finish` body `{requestId,roundId,summaryVersion}` -> saved summary plus `historyId`. roundId may be null before a round exists. Completion is explicit with zero/partial/all submitted questions, but rejects pending submissions with `409 PENDING_REVIEW`; it freezes whole-bank summary with history atomically and is replayable by identical request. Stale summaries return `409 SUMMARY_CONFLICT`.
- `POST /api/collections/{kind}/{id}/restart` body `{requestId,roundId,summaryVersion}` -> `{restarted:true}`. The completed live summary offers “再练一次”; this clears every current answer, result and whiteboard in one atomic write, advances revisions and grading generations, and leaves all frozen history unchanged. Unfinished practice returns `409 PRACTICE_NOT_FINISHED`; stale summaries return `409 SUMMARY_CONFLICT`. Identical requests replay without resetting new work, including after service restart. The host invalidates this collection's question cache and opens the first question. A failed subsequent load retries reading, without issuing another reset. This also works for extension samples and history-disabled page sessions; read-only history has no restart action.
- `GET /api/collections/{kind}/{id}/history` -> `{records:[{id,createdAt,updatedAt,status,collectionTitle,extension,submittedCount,gradedCount,pendingCount,questionCount,score,maxScore,summary?,...}]}` newest first; `GET .../history/{historyId}` adds `collection` (frozen question order and states), `questions:[{payload,page?}]`, and shared `page:{html,script,style,dependencies?}`. First submission starts a round and later submissions/reviews update it until explicit finish; finishing before any submission creates a frozen full-bank round. Completed history retains whole-bank `summary`; old/in-progress records without it retain submitted-question totals and pending counts. The next submission after completion starts a new round without carrying previous results. Content editing seals an active round as interrupted. Reads do not depend on the current bank/package; referenced SDK versions and images remain pinned independently. Round updates share the atomic state write with practice/receipt; receipt replay does not update progress or timestamps. Legacy single-question snapshots are read-only grouped by consecutive distinct IDs, with repeated IDs starting another group; only known frozen questions are included, per-entry page assets are retained when needed, and original stored records remain intact.
- `GET /api/collections/bank/{id}/questions/{qid}/editor` -> `{question:{id,title,data},extension,revision,contentVersion,draftVersion,editor:{apiVersion:{major:1,minor:5},html,script,style,dependencies?}|null}`. Raw data is returned only for explicit editing. draftVersion is stable across server restarts and guards editor-draft restoration; contentVersion remains the restart-scoped formal-edit guard. `POST .../edit` body `{requestId,revision,contentVersion,title,data}` -> `{collection,payload}`. Generic schema/rule validation and version checks precede durable writes. Raw-content edits reset only that question's answer/result/whiteboard draft; title-only edits preserve them. Both advance revision and retain history/other questions. A checksummed recovery journal commits bank and state together, including directory banks. Identical edit receipt replay returns its original confirmation; browser revalidates current data before mounting it.
- `GET/PUT/DELETE /api/editor-drafts/{bankId}/{qid}` saves incomplete authoring forms independently of question schemas and practice history. PUT `{contentVersion:<draftVersion>,draft:<opaque JSON object>,changed:boolean}` is capped at 1 MiB encoded and returns `{saved:true}`; GET returns that envelope, or `{draft:null}` when absent; DELETE returns `{deleted:boolean}`. This endpoint remains available for legacy or explicit clients. The current Web question editor does not read, write or restore authoring drafts: unsaved changes remain in the current page and are discarded on refresh. Old files are not automatically removed.
- `GET /api/sdk/quizforge.richtext/{version}` -> `{script,style}` for the static component; `GET .../editor` -> `{script}` for the heavy editor. Manifest/page/history keep only SDK references; The host archives all component files by immutable version.
- `POST /api/resources` body `{mime,data:base64}` -> `{id,mime,size}`; `GET /api/resources/{id}` -> authenticated image bytes. IDs are SHA-256 content hashes, permitted types are PNG/JPEG/WebP/GIF, and each image is capped at 4 MiB. These routes share existing API authentication and upload-origin validation.
- Non-2xx JSON errors: `{error:{code,message}}`.
- Saved questions are bound to canonical raw-data and fixed-version practice-package fingerprints. Directly changing saved question data or same-version practice package bytes refuses incompatible state with `409 COLLECTION_CHANGED` while preserving files; direct title/order changes remain compatible. Publish externally changed question content under a new bank ID and changed practice packages under a new extension version. The controlled edit endpoint retains the bank ID by updating question content and state fingerprints together, resets only changed raw-content practice, and preserves history; optional editor assets are excluded from the practice fingerprint.
- HTTP remains no-store; browser uses explicit bounded question/page/SDK caches and validates current stamps on question revisit or tab activation. Confirmed writes replace cached state. LRU and 5-minute idle timers release entries; collection close releases its question/unused page entries, and directory refresh clears question/page caches. Fixed SDK versions retain their independent bounds. No hidden iframe DOM cache; only one active iframe/whiteboard runtime. Localhost remains the default listener; LAN opt-in uses local network settings with same-origin checks for writes and server-owned paths. Access tokens are sent in `X-QuizForge-Token`.


## Browser extension SDK

Host injects QF in sandbox iframe (allow-scripts only), scoped messages checked by iframe identity and session.

- `QF.page.register({onLoad,onFlush?,onDispose?})`: invokes onLoad(context) on initial load and confirmed state changes; returns initial context. onFlush must finish unsent input/uploads before a transition; onDispose cleans up runtime resources when the host releases the page.
- Ordinary page context `{mode:'practice'|'example'|'exam'|'history',question:{id,title,data},answer,result,status,capabilities:{canSave,canSubmit,canRetry,canReview}}`. Practice/example permissions follow current state; history always sets all write capabilities to false and uses the chosen frozen question payload, including unsubmitted questions. Exam context additionally carries `exam:{id,status,deadline}` and independent canSave/canSubmit permissions; see [exam mode](EXAM_MODE.md). Raw-question editing has the separate editor context described below.
- `QF.save({purpose:'draft'|'submit',data:{answer},answerStateId?})` or `QF.save({purpose:'review',data:{review:{score,feedback?}}})` -> `{ok:true,data:{status,result}}` or `{ok:false,error:{code,message}}`. Review is available only for eligible submitted questions in the active round.
- `QF.page.reportAnswerState({status,targetId?})` reports one unsubmitted parent/child progress update and returns `{ok:true,data:{status:"reported",stateId}}`. Requires API 1.3/answer-state. Associate the returned stateId with the same draft snapshot through answerStateId; see [answer-state contract](SUBQUESTION_OUTLINE.md#即时反馈与保存api-13).
- `QF.requestAction({action:'retry'|'previous'|'next'|'goToQuestion',params?})` same Reply.
- `QF.ui.resize()` optional; automatic ResizeObserver reports iframe height.
- `QF.editor.register({onLoad,getDocument,hasChanges?,exportDraft?,importDraft?,onFlush?,onDispose?})` in edit mode: context `{mode:'edit',question:{id,title,data},capabilities:{canEdit:true}}`; getDocument returns `{title,data}` (sync or async), hasChanges returns a boolean. Resumable editors provide exportDraft/importDraft for opaque unvalidated forms; onFlush drains pending changes/uploads, and onDispose releases editor resources. Host validates through scoped read-document requests, persists working forms before releasing an iframe, and restores only matching draftVersion. Changed legacy editors without draft support must save before switching. Ordinary QF.save/action writes are refused in editor/history mode. Editor fields and drafts retain input after validation/conflict errors.
- History context uses `mode:'history'` and disables save/submit/retry/review capabilities; host also blocks write requests independently of the plugin.
- After the last question, arrows and the outline open a host-owned score card with graded earned/whole-bank totals, pending count and a finish button. Finish is unavailable until submitted questions are graded; unsubmitted questions may remain. Its layout is independent of extension pages. The corresponding history card uses frozen `summary` and is read-only; old records without summary have no extra card.
- Editor arrows and outline navigate within the editor session. Unvalidated working forms are persisted before their iframe is released, including invalid intermediate input. Save-all restores and validates changed documents one at a time before sequential formal edits. Partial success is reported explicitly and unsaved drafts remain available.
- Optional API 1.1 `outline-items`: page/editor `onOutlineNavigate(itemId)` locates children after parent ready, reusing the same iframe within one parent. New banks declare host-owned `questions[].outline` to select a labelled parent (`outlineLabel` on its collection row) or ordered children (`outlineItems`). Pure rules `getOutlineItems(data)` remains a metadata fallback only for questions without an explicit outline. Matrix rendering is shared by new/old banks and history: children replace the parent button, without a reserved parent column, and consecutive identical parent types/versions share one matrix. History freezes labels/order and uses its original pages. Parent answers, question counts, score output and content fingerprints are unchanged by outline-only edits. See [subquestion outline contract](SUBQUESTION_OUTLINE.md).
- No extension-specific conditional branches in the host or host UI.


## Draft data

Draft has `{schemaVersion:1,viewport:{x,y,zoom},strokes:[{id,color,width,points:[{x,y,pressure}]}],paper:{color,pattern},layout?:{width,padding,top}}`. First entry to a new writable draft captures the visible canvas CSS width with zero host padding/top margin and saves it through the existing whiteboard action; width is finite within 100–10000, padding 0–100, top 0–200. Subsequent entries and frozen history retain that layout. Absence of layout preserves the legacy 760px world, 26px side padding and 34px top margin without rewriting old drafts. World coordinates; camera changes do not modify strokes. Whiteboard container overlays the question display; practice allows question interaction. Draft enables tools, local rendering, undo/redo, eraser, pan/zoom, pen-vs-touch and pinch, and paper choices. Emit changes only after committed gestures or initial layout capture; cancelled gestures do not add ink. Pointer events never await HTTP. Save through host action queue; wait for pending writes before navigating or closing tabs.

For rendering, tools and layout compatibility see [draft layout](COMPATIBILITY.md#草稿布局). History permits view changes but rejects ink edits; ordinary practice hides saved ink without changing it.

The draft camera is never saved: each question opens at a home view (card centred horizontally, 24px top margin, width-fitted up to 100%), and the host keeps each question's pan, zoom and scroll for the session. The draft "hand" tool lets learners use the question and pan the board with one tool. The host frame script reports, as geometry only (`interactive-regions`, at most 600 disjoint frame-pixel boxes), the visible boxes of links, buttons, inputs, selects, textareas, labels, summaries, editable content, interactive ARIA roles, focusable `[tabindex]`, `[data-qf-interactive]` and elements with `cursor:pointer`; disabled controls and anything inside `[data-qf-interactive="false"]` are skipped. Pointer input on those boxes goes to the page; elsewhere it pans. Pages need no API change; mark custom clickable elements with `data-qf-interactive` (or `cursor:pointer`) and large non-interactive wrappers with `data-qf-interactive="false"` when the default detection is wrong.


## Rich text, resources and manual review

- New manifest `requiresRichText:{major:1,minMinor:0,documentFormat:1,documentProfile:"advanced-v1",capabilities:["images","tables","math"]}` binds the public service and persisted document profile, not Tiptap or an implementation version. The four version/profile fields are required; capabilities are optional, unique and supported. Unknown fields or simultaneous old `dependencies` are rejected. The application registry `core/shared/richtext/service.json` selects the verified concrete provider. See [rich-text service](RICHTEXT_SERVICE.md).
- Legacy `dependencies:[{id:"quizforge.richtext",version:"1.0.0"}]` remains readable without rewriting manifests or banks. Known 1.0.0 uses `basic-v1`; known 1.1.0/1.1.1/1.1.2/1.1.3 uses the current `advanced-v1` provider. Unknown old versions remain exact. Page/editor assets carry the resolved exact `dependencies` and optional stable `contentApi`; history freezes both and never re-resolves old snapshots. Public component versions live in `core/shared/richtext/<version>/` and are pinned on use into `.state/sdk/`. Published versions stay immutable and retained for history. No component bytes are duplicated in bank documents or history page snapshots.
- `GET /api/sdk/{id}/{version}` returns lightweight `{script,style}`; `GET .../editor` returns heavy `{script}` only on editing. Current allowlist is `quizforge.richtext`; paths and versions are validated. The host injects nonce scripts into isolated iframe documents; `connect-src 'none'` remains unchanged. The parent and iframe permit `blob:` image sources.
- `QF.content` is an immutable service facade exposing `api:{major,minor,documentFormat,documentProfile,capabilities}` plus existing public document/render/editor helpers. The compatibility `version` describes the public API, not the provider release; `configure` and `_createEditor` are implementation details. Static rendering creates no editor. Each active iframe permits one editor; editing another field flushes and destroys the previous one. `basic-v1` supports basic paragraphs, headings, marks, lists, quotes, code and images referencing `attrs.assetId`; `advanced-v1` adds styles, image sizing/alignment, tables and math. Persisted documents never contain ephemeral blob URLs. Provider updates change `packageVersion` for cache freshness while preserving question `contentVersion`, state fingerprints and editor `draftVersion`.
- `QF.resources.put(File)` returns `{id,mime,size}` and `get(id)` returns `{url,mime,size}` with iframe-local blob URLs. Host-authenticated `POST /api/resources` accepts `{mime,data:base64}`; `GET /api/resources/{sha256}` returns binary. PNG/JPEG/WebP/GIF are capped at 4 MiB per resource; current frame loads at most 16 MiB. `.state/resources/` is content addressed, retained independently of movable banks, and not automatically pruned in this version.
- `QF.page.register` and `QF.editor.register` optionally accept `onFlush` and `onDispose`. The host waits for unsent input/uploads as well as outstanding requests before navigation. Entering score summary requires a successful flush, including in development mode; rejected saves or remaining unsaved input keep the current frame mounted without a discard confirmation. A recovered successful save clears the current runtime retention marker; other retained question frames remain protected. Editor hooks `exportDraft/importDraft` preserve invalid intermediate forms without formal schema validation. `GET/PUT/DELETE /api/editor-drafts/{bankId}/{questionId}` persists `{contentVersion,draft,changed}` up to 1 MiB. This draft contentVersion uses editor response `draftVersion`, stable across server restarts; formal edit requests retain the ordinary opaque contentVersion guard. Only current-page undo state is retained.
- There is one active question iframe and whiteboard runtime. Switching collections flushes pending input and releases the old iframe/whiteboard; cached payloads do not keep inactive editors mounted. Question/page/SDK resource caches are bounded independently by count, bytes and idle time. Installed extension count does not create editor instances.
- Rule registration adds optional `review(data,answer,review)`. Submit can return `{gradingStatus:"pending",score:null,maxScore,correct:null,feedback}`; ordinary numeric results lacking gradingStatus remain compatible as graded. `review` must return a graded numeric result. The host checks result shape and finite numbers; extensions own score ranges and steps.
- `QF.save({purpose:"review",data:{review:{score,feedback?}}})` uses existing action revision/contentVersion/requestId guards. Review requires a matching submitted question in the active round; changes update current state and that round atomically, retaining its ID. `capabilities.canReview` is supplied by the server and disabled in history/completed rounds.
- Summary adds `gradedCount`, `pendingCount` and row `gradingStatus`; pending row score is null, not a scored zero. Whole-bank max remains present, earned score sums only graded questions. Finish rejects pending submitted questions. Unsubmitted questions may still finish under existing rules; completion freezes the whole-bank summary and all question snapshots. History reads tolerate old result/summary shapes.

- Editor handles expose ready/getDocument/setDocument/focus/flush/isUploading/destroy; advanced-v1 adds setAdvanced/isAdvanced. Rich-text API 1.1/camera-capture adds capturePhoto(), synchronously invoked from a user click after readiness. Photos enter the ordinary image/assetId and upload lifecycle; see [photo contract](RICHTEXT_SERVICE.md#拍照作为答案图片).


## AI grading

- Optional targeted grading extends the existing calls, without a new endpoint family: `QF.ai.grade({targetId?,force?})`, `getTask({targetId?})` (current-task envelope) and `getTask({taskId})`. Omission means the whole question. Target IDs are stable local IDs, using the outline ID text constraints (1–128 characters, trimmed, no controls or angle brackets); the extension validates membership. `GET /ai/current?targetId=...` selects a child task. Task responses retain targetId; retry/confirm recover it from the stored task. The identifier is host routing metadata, never a required model-output field or an AI input document field.
- Rule hooks accept optional trailing contexts: `prepareAiGrading(data,answer,{targetId?,state})` selects material, and `review(data,answer,{score,feedback,targetId?},{state})` reads the latest saved result to merge one child's grade into a complete parent result. Legacy hooks may ignore extra arguments. Child tasks use separate task bindings and per-target grading generations, while sharing answer/content/round guards. One child adoption or targeted manual review does not invalidate siblings. Whole grading and child grading replace each other's bindings; whole manual review, reanswer, content edits and completion invalidate all child jobs. Finish waits for every bound whole/child job, and the existing bounded single worker executes requests sequentially.
- Child adoption atomically persists the extension's aggregate result, per-target `result.aiAssessments[targetId]`, task receipts and the active history snapshot. Whole grading retains `result.aiAssessment`. Stored bindings and target generations survive restart; old task/state documents with only aiTaskId remain supported. At most 256 targets are retained per question.
- With autoGrade enabled, a new successful submission invokes the same `prepareAiGrading(data,answer,{automatic:true,state})` hook. Return the ordinary six-field input for whole grading, or `{targets:[{targetId,input}]}` to select answered children and supply each child's ordinary input. A targets array may be empty to skip automatic grading, contains at most 256 unique valid IDs, and cannot mix whole and child jobs. Validate the complete plan before creating jobs. The host never infers targets from outlines; each child uses existing task/retry/adoption guards and `review` aggregation. One submission occupies one entry in the existing bounded single-worker queue, so large composites do not drop children solely for exceeding queue length. Receipt replays and disabled settings do not schedule jobs. Manual targeted preparation remains unchanged and receives no automatic flag; page code queries each known target with `QF.ai.getTask({targetId})` to display progress and refresh saved results.

- Optional rule hook `prepareAiGrading(privateData,submittedAnswer)` returns `{protocolVersion:1,question,answer,referenceAnswer,maxScore,scoreStep}`. `referenceAnswer` combines reference answers, explanations and grading criteria in one nonempty content list. Released rules may still send a separate nonempty `rubric`; the host validates and merges both into `referenceAnswer` without modifying released packages or old task snapshots. Each content list contains `{type:"text",text}` or `{type:"image",assetId,alt?}`. AI maxScore and scoreStep are finite positive request parameters, independent of the parent question and need not divide evenly. Preparation does not call getScore. The host checks response JSON shape, finite numeric score and nonempty bounded feedback; it never rejects, rounds or clamps a score for range or precision. Only malformed output triggers repair. No browser-supplied grading content is accepted.
- `capabilities.canAiGrade` follows the rule hook and active submitted round. History is read-only. `QF.ai.grade({force?})`, `getTask({taskId?})`, `retry({taskId})` and `confirm({taskId,candidateVersion?,score?})` return ordinary Reply values. A missing taskId for getTask reads `{task:currentTask|null}` without starting a model request. Other task values carry `taskId,status,candidate:{version,score,feedback},error?`; confirm returns `{taskId,status:"confirmed",payload}` and the host updates context from payload.
- Scoped routes under `/api/collections/{kind}/{id}/questions/{qid}/ai`: `POST /grade`, `GET /current`, `GET /tasks/{taskId}`, `POST /tasks/{taskId}/retry`, `POST /tasks/{taskId}/confirm`. The parent generates request IDs and rendered contentVersion. Task access checks collection and question scope; confirmation reads stored candidate feedback, never browser text. The existing extension `review` hook owns adoption, limits, rounding, subquestion mapping and aggregation into the final grade/correct result. getScore/result consistency is a persistence contract, not an AI scoring policy. Candidate metadata retains this request's maxScore so feedback distinguishes the AI suggestion from the extension's final score. Extension rejection preserves the previous result and does not trigger model-output repair.
- Jobs bind the active round, raw question and extension fingerprints, submitted-answer hash, submission generation and grading generation. HTTP runs outside the StateStore lock. Whiteboard revision increments are allowed; reanswer, edit, manual review, round completion/deletion and superseding requests prevent stale adoption. Current result and round snapshots are persisted atomically, with trusted host-generated AI assessment metadata and feedback using actual final result score/maxScore.
- Task states include queued/running/succeeded/failed/superseded/confirmed. A format-valid AI suggestion is automatically passed to the extension review hook; the extension's adopted result is persisted as the final grade with feedback, without separate user confirmation. The confirmed state records this durable adoption. The existing confirm call remains a compatible, guarded and idempotent path. User retry creates a child task; force regrading preserves the current grade until the new result is successfully applied. Repeated request IDs are deduplicated. Transient retries and one output repair share a maximum of 3 provider calls per task. Provider-side execution/billing after network timeout cannot be deduplicated without provider support.
- An unchanged target with a queued/running task reuses that task even when `force:true`; repeated clicks cannot enqueue duplicate model work for the same target. Force regrading remains available after completion or failure, and other child targets remain independent. Pages should disable that target's grading/regrading button while queued/running and restore it when the task settles.
- `AiGateway` / `AiProvider` is a single-call boundary. The initial OpenAI-compatible adapter uses bounded native Node HTTP/HTTPS requests, nonstream Chat Completions and configurable JSON/schema/text output mode. The request uses one host-owned system message and one user message with score parameters and three material sections: question, submitted answer, and reference answer plus grading criteria. Input resources are resolved by ResourceStore; model text is treated as untrusted grading output. Tokens, network deadlines, text/images, responses, worker queue and task memory are bounded.
- `GET/PUT /api/settings/ai` and explicit `POST /api/settings/ai/test` manage the active profile. Only the loopback management server can update or test; authenticated remote clients may use grading and read masked status. `GET /api/settings/ai/credential` returns `{apiKey}` only at the loopback management endpoint (including Host/forwarding checks), with no-store; remote connections are denied. The local password field restores the saved value, supports replacement or deletion (`clearApiKey:true`), and clears its DOM value on close. No key is returned in ordinary settings status, diagnostics, task, answer/history, extension context or safe provider errors. Legacy API empty keys still retain the saved value unless clearApiKey is true.
- The simplified settings UI hides vision/output mode/output budget/timeout. New profile defaults are 8192 output tokens and 90 seconds, with existing explicit values preserved. Explicit diagnostics save current UI input, then test text response, exact grading JSON and actual visual recognition using a locally generated six-character random PNG. The expected text appears only in the image sent to the model; HTTP success alone never enables vision. A rejected JSON option falls back to text mode. Up to three requests, each capped at 35 seconds and 2048 output tokens, use only synthetic material and return safe checks/summary/time/call count, never raw model output or credentials. Successful visual recognition enables vision; mismatch, transport errors and skipped tests remain distinct. Reports and detected mode/vision persist with the profile, reject stale configuration adoption, and invalidate on endpoint/model/key/output-mode changes. Tests do not require enabling AI scoring and never toggle enabled/autoGrade.
- The AI profile adds `autoGrade:boolean`, default false when absent in older saved profiles. Settings updates may omit it to preserve the saved value. When AI is enabled and autoGrade is true, submitting an eligible question schedules its scoring; the card's manual AI button remains available. Settings status exposes this boolean without credentials, and only the loopback management server may change it.
- AI short-answer capabilities publish as extension 1.1.0, keeping the existing 1.0.0 bytes and banks intact. Public rich-text 1.0.0 remains unchanged; a pure converter produces ordered text/image blocks inside the new rule bundle.


## Exam orchestration

Bank `features.exam` defaults to true and adds an exam entry while preserving practice; only explicit false disables it. The bank file declares feature policy; catalog editing only renames or moves items. The host freezes a separate attempt, saves drafts without per-question submission, enforces server deadlines, locks all answers before whole-paper grading, and permits failed AI jobs to retry or use manual review before completion. Existing rule hooks are reused; pages receive `mode:"exam"` and independent save/submit capabilities. Persistent attempts use immutable question/package snapshots and a bounded lazy cache; history-disabled attempts and uploaded answers stay in their original browser page session. Completed exams join their source bank's existing history list/read/delete endpoints as `id:"exam-{examId}",mode:"exam",examId`, preserving frozen pages, navigation and read-only drafts; the exam entry shows only unfinished attempts and grading issues. Its confirmed delete action uses `DELETE .../exam` to persist cancellation before invalidating an unfinished attempt; deleted attempts cannot resume, time out, accept AI results or reappear after restart. Completed attempts use history deletion instead. Public endpoints and page adaptation are specified in [exam mode](EXAM_MODE.md).

## Unified collections and completion

There is one editable bank/extension state. Catalog kinds are bank and extension; developmentEnabled is retained only as the management-entry display setting. Legacy development references/markers/routes are compatibility aliases. Publication returns 410 PUBLICATION_REMOVED. Package format 3 installs a new physical bank/extension bundle on every import; old archive formats are rejected while installed old content remains readable. See [package and migration contract](LIBRARY_PACKAGES.md).

### Package import HTTP

Local-only endpoints retain origin and administrator-listener validation:

- POST /api/library/export with exactly one of {group:<physical bank group name>} or {bank:<physical bank path relative to question-banks, e.g. group/bank or bank>} returns format 3 .qbank. Group export includes all group banks; individual export includes only the selected bank and its actual dependencies and sets manifest scope to bank. Group export omits scope (equivalent to group). Download names use the selected folder name. Unknown/multiple selectors are rejected.
- POST /api/library/import uploads binary application/vnd.quizforge.qbank. Optional X-QuizForge-Filename is encodeURIComponent(original filename); its .qbank base name determines the new group or root bank name. Without the header, the manifest group is used. A scope:bank archive must contain exactly one bank and installs it directly at the bank root; an ordinary group archive stays grouped even with one bank.
- The Windows launcher accepts a local .qbank argument (or --import <file>) and streams its bytes to this same endpoint after its owned service is ready; HTTP does not accept a local filesystem path. Existing trays receive native requests through the current-user named pipe. A successful launcher open supplies only the installed bank route via imported-bank in the new browser URL; the page matches it against its local catalog and consumes the hint. Existing answer tabs are not reloaded.
- Native Hub protocol v1 accepts only --open-url "quizforge://hub/import?v=1&pack=<lowercase UUID>&revision=<positive integer>" with no other arguments. Exact fields, no duplicates/encoding, maximum 1024 characters; revision has no leading zeros and is at most 9007199254740991. Installation registers the current-user URL protocol without taking over another owner; ZIP/source do not register it. Current-user pipe messages are exactly {command:"hub-import",uri:<validated full URI>}; sender and receiver both validate. There is no public HTTP wakeup, download-URL or local-path control endpoint.
- The native client uses the fixed official origin https://quizforge.treenewbee.cloud, requests /api/packs/<id>/local-import?revision=<revision> (JSON, at most 32 KiB), then /download?revision=<revision>&sha256=<manifest hash> under the same pack path. Validate schemaVersion:1, pack identity/revision, archive name ending .qbank, integer size 1–67108864, lowercase SHA-256. System TLS/certificate validation, no redirects/proxy/cookies/default credentials; 180 seconds for both network requests together, no automatic retry. Stream to a random owned task directory, match Content-Length/actual size/hash, then use the same binary import route. The fixed staging basename is not sent as X-QuizForge-Filename, so the package manifest determines the installed name. Format 3 only; no old-package migration.
- Hub and local files share one serial queue and a 20-pending-task limit. Pending hub:<packId>:<revision> jobs coalesce; reopening after completion installs another independent copy. --status pendingImports/lastImport include source, packId, revision and queued/downloading/importing/completed/failed; cleanup failures also appear in hubCleanupWarning and logs/hub-import.log. Only stale owned task directories older than 24 hours are cleaned at the next backend readiness. This changes no extension API or persisted question/history schema. Hub server/web deployment and real browser acceptance remain separate from implementing this client.
- Successful import returns {scope:'bank'|'group',name,path,group,extensionGroup,importedBanks,importedExtensions,catalog}; group is empty for a root bank. Every import creates an independent copy. The destination bank/group and extension group names are allocated separately and incoming references are remapped to installed extension paths. Existing content and progress are preserved. No replacement choices, skipped duplicates or pending plans.
- Format 1/2 packages return 422 UNSUPPORTED_LIBRARY_ARCHIVE with author-upgrade guidance. The retired /import/commit and /import/cancel endpoints return 410 IMPORT_CHOICES_REMOVED.
- POST /api/library/manage maps bank names and groups to filesystem operations. Extension create/update operations return 403 EXTENSION_STRUCTURE_READ_ONLY. Deleting an extension or physical group checks bank references before archiving; an in-use target returns 409 EXTENSION_IN_USE.
- Bank/group deletion archives only the selected bank or bank group and preserves every extension directory. It does not scan bank contents or resolve dependencies for extension cleanup. The response includes archivedTo; the legacy removedExtensionGroups and retainedExtensionGroups arrays are always empty and do not enumerate preserved extensions. No dependency cleanupWarning is returned. The recovery receipt records the selected source and destination; move failures roll back completed moves. Answers and frozen history are preserved. Explicit extension deletion retains its reference protection.
- Collection overviews include `revision` (the collection content revision, separate from each answer's numeric revision). Management responses include `catalog` and `retainedCollections:[{kind,id,previousRevision,revision,title}]`. These receipts identify already loaded collections whose question, resource and extension inputs remain unchanged after a directory operation. A client displaying `previousRevision` may update its title and revision in place; other revisions must reload normally. Pure bank/group renames preserve the mounted answer page and reuse validation. Receipts do not change answer revisions or frozen history.

New references use {path:"extensions/<group>/<extension>"}; old optional id is checked if present. New copies have host-owned local bank identities (g.<instanceId>) independent of author metadata, with bank:<routeId>:mixed state keys. Extension page route IDs derive from physical paths. Catalog and collection titles use filesystem names. Same-source IDs/versions may coexist without sharing practice state. All current banks and extension examples require exact self-consistent paths; ID/version-only and development bindings, flat extensions, standalone JSON banks and development collection routes return explicit upgrade errors. Full manifests no longer inherit development.json configuration. Saved-state recovery and frozen history decoding remain available. Physical extension groups replace logical memberships; old tables are not used or deleted.

See [physical packages](LIBRARY_PACKAGES.md) for archive format, names, resources and state preservation.

Old .development/.state answers are copied lazily to .state with original and backup retained. Frozen history is unchanged. Source edits invalidate affected current answers, with a before-content-edit backup; immutable public SDK and history assets stay pinned.

POST /api/collections/{kind}/{id}/finish retains requestId, roundId and summaryVersion. It first submits saved answered drafts through extension grading, then completes the round. Summary adds answeredUnsubmittedCount. Declared answer-state types determine answered state explicitly; legacy saved drafts are submitted as-is so extension rules own empty/partial answers. Previously submitted questions are retained. Save/grade failures keep answers and permit retry; request receipts prevent duplicate submission/completion. Pending AI/manual grades return completionPending:true, finished:false and pendingCount; they remain available for retry/manual review. A later finish finalizes the same round after grades are confirmed. Stale summary and content/revision checks remain enforced.

New draft layout width is 760 logical pixels, independent of device width. Saved legacy layouts are retained. Zoom/pan are device-local views and do not mutate persisted viewport; stroke and paper edits persist normally. No extension API version bump.
