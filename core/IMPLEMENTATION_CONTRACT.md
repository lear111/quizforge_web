# QuizForge Web v1 implementation contract

Scope: local/LAN Java server, manual question-bank/extension folders, tabbed practice/example UI, outline, single-choice and rich-text short-answer extensions, persistent answers and per-question whiteboard, collection-round history, and extension-owned question editing. No workspace or import UI. Independent of QuizForge V2.

## Folders and extension contract

Paths in this document are relative to the product root passed as `--root`. The root contains `core/`, `extensions/`, `question-banks/`, `skills/`, the startup scripts and README. Application code, public SDK, dependencies, build files, tests and developer documentation live under `core/`; builds run from that directory. Runtime resources resolve to `core/web/`, `core/server/`, `core/shared/` and `core/node_modules/`. Practice state remains under the product root's `.state/`.

- `question-banks/*.json` or `question-banks/<folder>/bank.json`: `{id,title,description?,extension?:{id,version},questions:[{id,title,extension?:{id,version},data}]}`. Root extension is a default; per-question references override it, and every question needs a valid effective reference. Question `data` is owned by its extension. Directory banks carry independent images in `assets/`; resource references use content IDs, not filesystem paths or base64 documents.
- `extensions/<folder>/manifest.json`: `{id,version,name,description,entry,script,style,rules,questionSchema,answerSchema,examples,dependencies?}`. All declared file paths are relative to that folder; dependencies are public SDK `{id,version}` references.
- `examples` file: same question-bank shape (ID `examples`); backend catalog exposes it as a preview collection. Preview answers/ink are separate from real banks.
- `.state/`: Java-owned current practice, per-question whiteboard, collection-round history with frozen practice assets, bounded request receipts, and edit recovery journal. Independent subdirectories preserve editor drafts, immutable resources and pinned public SDK versions. Completed rounds are immutable; active rounds update with submissions and confirmed reviews. Current state and history share the 32 MiB collection-file limit; reaching it rejects new writes without silently pruning old history.
- Optional `extensions/<folder>/editor.json`: `{entry,script,style}` for an extension-owned raw-question editor; these editor assets do not alter the immutable practice package fingerprint.
- Practice/example views receive only extension `project(data, {submitted,result})` output; history receives its frozen public projections, including unsubmitted questions. The explicit editor endpoint returns raw question data, including answer keys, for authoring through the same authenticated API.
- Rules script calls `QF.defineType({project,validateQuestion?,validateAnswer?,grade,getScore?,review?})`. `grade(data,answer)` returns a numeric `{score,maxScore,correct,feedback}` result, optionally marked `gradingStatus:"graded"`, or a pending `{gradingStatus:"pending",score:null,maxScore,correct:null,feedback}` result. `review(data,answer,review)` must return a graded numeric result; each extension validates its own manual-score steps. Optional `getScore(data,state)` returns `{score,maxScore}` with finite nonnegative maxScore, null score only for pending submissions, and otherwise finite `0 <= score <= maxScore`; state includes status/answer/result/revision and a submitted boolean. Extensions own grading and score output; Java aggregates only graded earned scores, counts pending submissions separately, and counts unsubmitted questions as zero while retaining their maximum. The runner adapts existing single-choice 1.0.0 from submitted results or unsubmitted public projection maxScore. Schema validation uses AJV in the rules runner. Rules have JSON input/output and run synchronously in a deadline-limited child process with restricted filesystem permissions; local administrator-supplied plugins only in v1 (not a full hostile-code OS sandbox).

## HTTP contract

Mixed binding details: a bank using any question-level reference (or omitting the root default) has `extension:null` and an `extensions` array in collection metadata; each outline row and question response identifies its own effective extension. Its state identity is `bank:<id>:mixed`; legacy root-only banks retain `bank:<id>:<extensionId>:<version>`. Switching a practiced bank's binding layout by hand requires a new bank ID, as with other external content changes. The unique extension set and aggregate fingerprint are computed once when loading a collection. Batch validation/projection/scoring groups by ID/version/fingerprint with sequential bounded chunks and restores original order. Mixed history uses immutable `pages[pageKey]` resources and per-question `pageKey` references, validates identities/references on read, and keeps legacy `round.page` snapshots readable. No active-instance or cache capacity is increased.

- `GET /api/catalog` -> `{banks:[{id,title,description,questionCount,extension:{id,version},error?}],extensions:[{id,version,name,description,questionCount,error?}]}`. Bad entries are reported separately without breaking good entries. Directory rescanned on refresh.
- `GET /api/collections/{kind}/{id}` where kind is `bank` or `extension` and extension id means extension ID -> `{id,title,kind,extension:{id,version,name}|null,extensions:[{id,version,name}],questions:[{id,title,type:{id,version,name}}],states:{[questionId]:{status,answer,result,revision}},error?}`. Matrix groups adjacent equal type ID/version pairs without changing question order. Mixed banks resolve each question's extension; legacy root-level bindings remain compatible.
- `GET /api/collections/{kind}/{id}/questions/{qid}` -> `{extension:{id,version,name},stamp:{revision,contentVersion,packageVersion},question:{id,title,data},state:{status,answer,result,revision},capabilities:{canReview},draft:{schemaVersion:1,viewport:{x,y,zoom},strokes:[],paper:{color,pattern}}}`. `question.data` is public projection. Missing whiteboard draft may be null. status is `unanswered`, `draft`, or `submitted`; result is null until submit and can then be pending or graded. canReview requires a matching submitted manual result in the current active round and is false after completion.
- `GET /api/collections/{kind}/{id}/questions/{qid}/stamp` -> `{revision,contentVersion,packageVersion}`. Warm reads verify content/state without Node projection. Opaque keyed versions reset on server restart. Browser checks them before reusing cached public payloads; packageVersion shares page assets across questions.
- `GET /api/extensions/{id}/{version}/page` -> `{html,script,style,dependencies?:[{id,version}]}`. Backend reads only manifest-declared page assets and supported SDK references. It does not expose rule files, schemas, or raw bank JSON through static hosting.
- `POST /api/collections/{kind}/{id}/questions/{qid}/actions` body `{requestId,revision,contentVersion?,action,data}`; action `draft` (`data.answer`), `submit` (`data.answer`), `review` (`data.review:{score,feedback?}`), `retry` (`data:{}`), `whiteboard` (`data.draft`). Successful reply is the same full question response as GET. Revision guards all writes, including reviews; review also requires an eligible active-round submission and atomically updates current state and the same history round. Browser captures the displayed question's contentVersion when enqueueing a write; a mismatch returns `409 CONTENT_CONFLICT` before grading or persistence. Failed retries retain that version until explicit server reload remounts the question. Persist bounded request receipts so identical replay returns its existing result, including after server restart, and reused ID with different request fails. Revision conflict HTTP 409.
- `GET /api/health` -> `{ok:true}`.
- `GET/PUT /api/settings/network` are local management endpoints, requiring the main loopback listener, loopback peer and loopback Host plus write-origin validation. Response `{canManage,enabled,port,passwordConfigured,urls,error?}`; PUT `{enabled,port,password?}`. Empty/omitted password retains the current verifier; initial enable requires at least 8 characters. An independent LAN listener shares the same library and state store. `.state/network-settings.json` stores configuration and a salted PBKDF2 verifier; never plaintext passwords. Disable/password changes revoke LAN sessions.
- `POST /api/auth/login` accepts `{password}` and returns `{token}`. LAN API calls use the returned short-lived random token through `X-QuizForge-Token`; the browser stores only this session token. Login is origin-checked and rate-limited. Existing command-line token authentication remains compatible. Settings do not edit the OS firewall or add per-user practice state.
- `GET /api/collections/{kind}/{id}/summary` -> `{score,maxScore,submittedCount,gradedCount,pendingCount,questionCount,finished,status,roundId,summaryVersion,questions:[{id,score,maxScore,submitted,gradingStatus}]}`. Pending row score is null; aggregate score includes graded results only. `POST .../finish` body `{requestId,roundId,summaryVersion}` -> saved summary plus `historyId`. roundId may be null before a round exists. Completion is explicit with zero/partial/all submitted questions, but rejects pending submissions with `409 PENDING_REVIEW`; it freezes whole-bank summary with history atomically and is replayable by identical request. Stale summaries return `409 SUMMARY_CONFLICT`.
- `GET /api/collections/{kind}/{id}/history` -> `{records:[{id,createdAt,updatedAt,status,collectionTitle,extension,submittedCount,gradedCount,pendingCount,questionCount,score,maxScore,summary?,...}]}` newest first; `GET .../history/{historyId}` adds `collection` (frozen question order and states), `questions:[{payload,page?}]`, and shared `page:{html,script,style,dependencies?}`. First submission starts a round and later submissions/reviews update it until explicit finish; finishing before any submission creates a frozen full-bank round. Completed history retains whole-bank `summary`; old/in-progress records without it retain submitted-question totals and pending counts. The next submission after completion starts a new round without carrying previous results. Content editing seals an active round as interrupted. Reads do not depend on the current bank/package; referenced SDK versions and images remain pinned independently. Round updates share the atomic state write with practice/receipt; receipt replay does not update progress or timestamps. Legacy single-question snapshots are read-only grouped by consecutive distinct IDs, with repeated IDs starting another group; only known frozen questions are included, per-entry page assets are retained when needed, and original stored records remain intact.
- `GET /api/collections/bank/{id}/questions/{qid}/editor` -> `{question:{id,title,data},extension,revision,contentVersion,draftVersion,editor:{html,script,style,dependencies?}|null}`. Raw data is returned only for explicit editing. draftVersion is stable across server restarts and guards editor-draft restoration; contentVersion remains the restart-scoped formal-edit guard. `POST .../edit` body `{requestId,revision,contentVersion,title,data}` -> `{collection,payload}`. Generic schema/rule validation and version checks precede durable writes. Raw-content edits reset only that question's answer/result/whiteboard draft; title-only edits preserve them. Both advance revision and retain history/other questions. A checksummed recovery journal commits bank and state together, including directory banks. Identical edit receipt replay returns its original confirmation; browser revalidates current data before mounting it.
- `GET/PUT/DELETE /api/editor-drafts/{bankId}/{qid}` saves incomplete authoring forms independently of question schemas and practice history. PUT `{contentVersion:<draftVersion>,draft:<opaque JSON object>,changed:boolean}` is capped at 1 MiB encoded and returns `{saved:true}`; GET returns that envelope, or `{draft:null}` when absent; DELETE returns `{deleted:boolean}`. Browser checks the stable version before restoring and retains conflicting drafts.
- `GET /api/sdk/quizforge.richtext/{version}` -> `{script,style}` for the static component; `GET .../editor` -> `{script}` for the heavy editor. Manifest/page/history keep only SDK references; Java archives all component files by immutable version.
- `POST /api/resources` body `{mime,data:base64}` -> `{id,mime,size}`; `GET /api/resources/{id}` -> authenticated image bytes. IDs are SHA-256 content hashes, permitted types are PNG/JPEG/WebP/GIF, and each image is capped at 4 MiB. These routes share existing API authentication and upload-origin validation.
- Non-2xx JSON errors: `{error:{code,message}}`.
- Saved questions are bound to canonical raw-data and fixed-version practice-package fingerprints. Directly changing saved question data or same-version practice package bytes refuses incompatible state with `409 COLLECTION_CHANGED` while preserving files; direct title/order changes remain compatible. Publish externally changed question content under a new bank ID and changed practice packages under a new extension version. The controlled edit endpoint retains the bank ID by updating question content and state fingerprints together, resets only changed raw-content practice, and preserves history; optional editor assets are excluded from the practice fingerprint.
- HTTP remains no-store; browser uses explicit bounded question/page/SDK caches and validates current stamps on question revisit or tab activation. Confirmed writes replace cached state. LRU and 5-minute idle timers release entries; collection close releases its question/unused page entries, and directory refresh clears question/page caches. Fixed SDK versions retain their independent bounds. No hidden iframe DOM cache; only one active iframe/whiteboard runtime and up to 8 tabs. Localhost remains the default listener; LAN opt-in uses local network settings or the compatible launcher flag, with same-origin checks for writes and server-owned paths. Access tokens are sent in `X-QuizForge-Token`.

## Browser extension SDK

Host injects QF in sandbox iframe (allow-scripts only), scoped messages checked by iframe identity and session.

- `QF.page.register({onLoad,onFlush?,onDispose?})`: invokes onLoad(context) on initial load and confirmed state changes; returns initial context. onFlush must finish unsent input/uploads before a transition; onDispose cleans up runtime resources when the host releases the page.
- Ordinary page context `{mode:'practice'|'example'|'history',question:{id,title,data},answer,result,status,capabilities:{canSave,canSubmit,canRetry,canReview}}`. Practice/example permissions follow current state; history always sets all write capabilities to false and uses the chosen frozen question payload, including unsubmitted questions. Raw-question editing has the separate editor context described below.
- `QF.save({purpose:'draft'|'submit',data:{answer}})` or `QF.save({purpose:'review',data:{review:{score,feedback?}}})` -> `{ok:true,data:{status,result}}` or `{ok:false,error:{code,message}}`. Review is available only for eligible submitted questions in the active round.
- `QF.requestAction({action:'retry'|'previous'|'next'|'goToQuestion',params?})` same Reply.
- `QF.ui.resize()` optional; automatic ResizeObserver reports iframe height.
- `QF.editor.register({onLoad,getDocument,hasChanges?,exportDraft?,importDraft?,onFlush?,onDispose?})` in edit mode: context `{mode:'edit',question:{id,title,data},capabilities:{canEdit:true}}`; getDocument returns `{title,data}` (sync or async), hasChanges returns a boolean. Resumable editors provide exportDraft/importDraft for opaque unvalidated forms; onFlush drains pending changes/uploads, and onDispose releases editor resources. Host validates through scoped read-document requests, persists working forms before releasing an iframe, and restores only matching draftVersion. Changed legacy editors without draft support must save before switching. Ordinary QF.save/action writes are refused in editor/history mode. Editor fields and drafts retain input after validation/conflict errors.
- History context uses `mode:'history'` and disables save/submit/retry/review capabilities; host also blocks write requests independently of the plugin.
- After the last question, arrows and the outline open a host-owned score card with graded earned/whole-bank totals, pending count and a finish button. Finish is unavailable until submitted questions are graded; unsubmitted questions may remain. Its layout is independent of extension pages. The corresponding history card uses frozen `summary` and is read-only; old records without summary have no extra card.
- Editor arrows and outline navigate within the editor session. Unvalidated working forms are persisted before their iframe is released, including invalid intermediate input. Save-all restores and validates changed documents one at a time before sequential formal edits. Partial success is reported explicitly and unsaved drafts remain available.
- No extension-specific conditional branches in Java or host UI.

## Whiteboard module API

`mountWhiteboard(container, {onChange,onInteractionChange?,onFullscreen?,toolbarContainer?})` returns `{load(draft|null),getDraft(),setViewport(camera,{emit?}),setViewCamera(camera|null),getViewCamera(),setFullscreenState({supported,active,pending}),setMode('practice'|'draft'),flush(),destroy()}`. An optional dedicated toolbar container keeps screen-space controls outside the question viewport. View camera is a practice-only display override shared by question and ink; it never changes persisted draft camera, geometry or undo history. Practice centers the card (long cards scroll normally); draft preserves its own pan/zoom. Fixed navigation remains outside the transformed world.
Draft has `{schemaVersion:1,viewport:{x,y,zoom},strokes:[{id,color,width,points:[{x,y,pressure}]}],paper:{color,pattern}}`. World coordinates; camera changes do not modify strokes. Whiteboard container overlays the question display; practice makes ink read-only and allows question interaction. Draft enables tools, local rendering, undo/redo, eraser, pan/zoom, pen-vs-touch and pinch, and paper choices. Emit changes only after committed gestures; cancelled gestures do not add ink. Pointer events never await HTTP. Save through host action queue; wait for pending writes before navigating or closing tabs.

Default paper is plain white. Paper is a separate background sibling below the question stage; only the transparent ink overlay stays above the question. Paper follows the same camera and scroll compensation, is visible only in draft mode, and is removed on destroy. Its color is opaque while grid/dot marks are translucent; practice backgrounds are white.

Selection passes pointer input through to the question without leaving draft or changing saved ink/camera. The host owns browser fullscreen: its icon appears only in the draft toolbar on supported browsers, requests fullscreen synchronously from a click with navigation UI hidden, follows fullscreenchange, and exits app-owned fullscreen when the active view no longer supports draft. While active, a temporary shell class hides both sidebars and the tab/document headers, expands the question pane, and keeps tools, exit control and floating question arrows available. Exiting restores the existing sidebar preferences without rewriting camera or ink. Fullscreen state is transient and never saved in question data.

## Rich-text and manual-review upgrade (2026-10-08)

- Existing root JSON banks remain compatible. Directory banks use `question-banks/<folder>/bank.json` and `assets/`; controlled edits export referenced immutable image resources into that directory. Root `extension` is an optional default; each question may specify its own exact `{id,version}`. Without a default every question must declare a reference. Extension example collections remain bound to their own package.
- Optional manifest `dependencies:[{id:"quizforge.richtext",version:"1.0.0"}]` is carried by page/editor/history assets. Public component versions live in `core/shared/richtext/<version>/` and are pinned on use into `.state/sdk/`. Same-version content changes refuse new dependencies, while pinned versions remain readable for history. No shared component bytes are duplicated in individual bank documents or history page snapshots.
- `GET /api/sdk/{id}/{version}` returns lightweight `{script,style}`; `GET .../editor` returns heavy `{script}` only on editing. Current allowlist is `quizforge.richtext`; paths and versions are validated. The host injects nonce scripts into isolated iframe documents; `connect-src 'none'` remains unchanged. The parent and iframe permit `blob:` image sources.
- `QF.content` exposes the public rich-text component. Static document rendering creates no editor. Each active iframe permits one editor; editing another field flushes and destroys the previous one. JSON `formatVersion:1` documents support paragraphs, headings, marks, lists, quotes, code and images referencing only `attrs.assetId`; persisted documents never contain ephemeral blob URLs.
- `QF.resources.put(File)` returns `{id,mime,size}` and `get(id)` returns `{url,mime,size}` with iframe-local blob URLs. Host-authenticated `POST /api/resources` accepts `{mime,data:base64}`; `GET /api/resources/{sha256}` returns binary. PNG/JPEG/WebP/GIF are capped at 4 MiB per resource; current frame loads at most 16 MiB. `.state/resources/` is content addressed, retained independently of movable banks, and not automatically pruned in this version.
- `QF.page.register` and `QF.editor.register` optionally accept `onFlush` and `onDispose`. The host waits for unsent input/uploads as well as outstanding requests before navigation. Editor hooks `exportDraft/importDraft` preserve invalid intermediate forms without formal schema validation. `GET/PUT/DELETE /api/editor-drafts/{bankId}/{questionId}` persists `{contentVersion,draft,changed}` up to 1 MiB. This draft contentVersion uses editor response `draftVersion`, stable across server restarts; formal edit requests retain the ordinary opaque contentVersion guard. Only current-page undo state is retained.
- There is one active question iframe and whiteboard runtime. Switching tabs persists/suspends the old editor and releases its iframe/whiteboard; inactive tabs retain metadata, and at most 8 tabs are accepted. Question/page/SDK resource caches are bounded independently by count, bytes and idle time. Installed extension count does not create editor instances.
- Rule registration adds optional `review(data,answer,review)`. Submit can return `{gradingStatus:"pending",score:null,maxScore,correct:null,feedback}`; ordinary numeric results lacking gradingStatus remain compatible as graded. `review` must return a graded numeric result. Range/result shape checks are generic; each extension owns score-step validation.
- `QF.save({purpose:"review",data:{review:{score,feedback?}}})` uses existing action revision/contentVersion/requestId guards. Review requires a matching submitted question in the active round; changes update current state and that round atomically, retaining its ID. `capabilities.canReview` is supplied by the server and disabled in history/completed rounds.
- Summary adds `gradedCount`, `pendingCount` and row `gradingStatus`; pending row score is null, not a scored zero. Whole-bank max remains present, earned score sums only graded questions. Finish rejects pending submitted questions. Unsubmitted questions may still finish under existing rules; completion freezes the whole-bank summary and all question snapshots. History reads tolerate old result/summary shapes.
- Short-answer 1.0.0 provides rich stem/answer/reference/rubric, 0.5-point manual score confirmation, editor and three demo questions. It does not require a host type-specific branch. Mixed-extension banks and advanced rich-text nodes are covered by later sections; audio/video, ZIP import/export and post-completion grading revisions remain outside this upgrade.

## AI grading upgrade (2026-10-08)

- Optional rule hook `prepareAiGrading(privateData,submittedAnswer)` returns `{protocolVersion:1,question,answer,referenceAnswer,rubric,maxScore,scoreStep}`. Each content list contains `{type:"text",text}` or `{type:"image",assetId,alt?}`. The host compares maxScore to both submitted result and extension scoring interface, and checks finite score range and exact scoreStep. No browser-supplied grading content is accepted.
- `capabilities.canAiGrade` follows the rule hook and active submitted round. History is read-only. `QF.ai.grade({force?})`, `getTask({taskId?})`, `retry({taskId})` and `confirm({taskId,candidateVersion?,score?})` return ordinary Reply values. A missing taskId for getTask reads `{task:currentTask|null}` without starting a model request. Other task values carry `taskId,status,candidate:{version,score,feedback},error?`; confirm returns `{taskId,status:"confirmed",payload}` and the host updates context from payload.
- Scoped routes under `/api/collections/{kind}/{id}/questions/{qid}/ai`: `POST /grade`, `GET /current`, `GET /tasks/{taskId}`, `POST /tasks/{taskId}/retry`, `POST /tasks/{taskId}/confirm`. The parent generates request IDs and rendered contentVersion. Task access checks collection and question scope; confirmation reads stored candidate feedback, never browser text. The existing extension `review` hook owns the adopted grade/correct result.
- Jobs bind the active round, raw question and extension fingerprints, submitted-answer hash, submission generation and grading generation. HTTP runs outside the StateStore lock. Whiteboard revision increments are allowed; reanswer, edit, manual review, round completion/deletion and superseding requests prevent stale adoption. Current result and round snapshots are persisted atomically, with trusted host-generated AI assessment metadata and feedback using actual final result score/maxScore.
- Task states include queued/running/succeeded/failed/superseded/confirmed. Success produces a candidate, not a final grade. User retry creates a child task; force regrading preserves current grade until confirmation. Repeated request IDs are deduplicated. Transient retries and one output repair share a maximum of 3 provider calls per task. Provider-side execution/billing after network timeout cannot be deduplicated without provider support.
- `AiGateway` / `AiProvider` is a single-call boundary. The initial OpenAI-compatible adapter uses one shared Java HttpClient, nonstream Chat Completions and configurable JSON/schema/text output mode. Input resources are resolved by ResourceStore; model text is treated as untrusted grading output. Tokens, network deadlines, text/images, responses, worker queue and task memory are bounded.
- `GET/PUT /api/settings/ai` and explicit `POST /api/settings/ai/test` manage the active profile. Only the loopback management server can update or test; authenticated LAN may use grading and read masked status. `.state/ai/profile.json` permissions are restricted; no API key is returned in settings, task, answer/history, extension context or safe provider errors. Empty API Key retains the saved value; `clearApiKey:true` clears it. Connection test invokes the saved model once and does not return generated text.
- AI short-answer capabilities publish as extension 1.1.0, keeping the existing 1.0.0 bytes and banks intact. Public rich-text 1.0.0 remains unchanged; a pure converter produces ordered text/image blocks inside the new rule bundle.

## Core organization and compatible short-answer upgrade (2026-10-08)

- `CollectionRoutes` owns collection dispatch; HTTP authentication, Host/Origin checks, body bounds and response handling stay in `QuizForgeServer`.
- `AiGradingProtocol` holds pure input validation and final feedback formatting. State transactions, freshness and idempotency stay in `StateStore`.
- `core/web/extension-requests.js` routes the extension protocol through injected persistence/navigation operations; `core/web/practice-context.js` contains pure view context and navigation helpers. `core/web/app.js` coordinates lifecycle and save barriers.
- The normal launcher opts into `--upgrade-short-answer` before accepting requests. Known short-answer 1.0.0, 1.1.0 and 1.2.0 banks upgrade to installed 1.2.1. Preserve bank/question IDs, original stem content, assets and original version state/history; only pre-1.2 titles are merged into the stem. In-progress answers, grades and ink seed a new active round; completed-round answers restore as drafts. No old history or released package is rewritten. Existing destination state refuses overwrite. Bank reference and new state use the edit journal. Same-root services must not run concurrently.

## Advanced rich text and unified short-answer stem (2026-10-08)

- Public SDK 1.1.0 and short-answer 1.2.0 are independent new packages. The new SDK accepts existing formatVersion:1 documents and adds text styles, highlight, sub/superscript, paragraph alignment/line height, image width/alignment, tables and inline/block LaTeX math. The versioned document validator and extension schemas enforce attributes and resource references; ordinary and history static rendering use the same document styles as editing.
- SDK 1.1.1 and short-answer 1.2.1 preserve those features under new immutable versions. A valid existing SDK archive is authoritative for its version; changed source bytes never replace it. New features require a new version. Dependency failures retain their actual error code and detail, and an invalid upgrade target is distinguished from a missing installation.
- Inline editing has a basic toolbar and a top-right advanced toggle. Expansion retains the existing editor/iframe, selection and undo stack. The measured inline text-column width remains fixed inside the advanced workspace, with shared font, margins and rendering. Short-answer authoring and practice use the same 704px card and responsive padding. A narrower screen can scroll the expanded document without changing its captured wrapping width.
- The iframe's scoped editor-layout request requires editable current context and finite width within bounds. The shell expands the existing pane/iframe in place, suspends camera resizing, and restores geometry on close/dispose. History cannot open editing. Advanced workspace state is transient, never part of answers or whiteboard state.
- New short-answer practice and authoring have only the rich stem rather than a separate visible title. Authoring derives generic question metadata title from the stem; the HTTP contract and other question types remain compatible. Table cells and LaTeX formulas are converted into explicit AI content, not silently dropped by text extraction.
- Extension catalog preview rows expose the latest usable version per type ID, matching preview routing; older packages remain available to version-bound banks and history.

## Ownership

- Backend agent: `core/pom.xml`, `core/src/main/java`, `core/src/test/java`, `core/server/`, `core/package.json`, Node rule engine tests. Do not touch frontend/sample folders.
- Extension agent: `extensions/`, `question-banks/`. Do not touch SDK/host.
- Whiteboard agent: `core/web/whiteboard.js`, `core/web/whiteboard-model.js`, `core/web/whiteboard.css`, `core/test/whiteboard*.test.mjs`. Do not touch other UI.
- Root: frontend shell/SDK/HTTP adapter, launchers, documentation and integrated verification.
