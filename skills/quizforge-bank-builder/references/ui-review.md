# 前端原型与交互评审

在任何完整题库的批量生成之前读取本文件，包括全部复用已有拓展的情况。目的是让用户先看到材料变成题卡后的实际效果，确认后再投入实现和批量转换。

## 第一阶段应交付什么

1. **选型与内容方案**：各类题／复杂变体对应的精确拓展版本，如何保留共享题干、小问、图表和作答形式；替代、遗漏与接口缺口。
2. **可查看的代表题原型**：未提交、提交后、编辑三个状态，使用同一材料实例和清楚标记的样例答案／反馈。
3. **交互方案**：控件的动作、状态变化、失败反馈与保存／判分归属。
4. **待确认决定**：具体指向原型和交互，而不是只问“能否创建拓展”。交付后停止，等待答复。

不要将“所有题型可覆盖”当作完成 UI 评审。不要让用户读 schema、JSON 或代码来想象界面。不要先做整库再以“可随时调整”代替确认。

## 代表题怎么选

每种不同的呈现／作答方式至少一个材料中的实例。优先包含容易产生问题的版式：长题干、图片及图注、表格、公式、共享材料和多个小问。相同交互、仅内容不同的题无需逐道画原型；只展示简单短题不足以评审复杂变体。

只读取现有拓展的声明、schema、页面和示例来核实 UI 能力。复用的题卡外观与行为必须对应精确安装版本；缺少想要的控件时说明现有边界，申请新拓展或接受替代。不能以原型暗示改旧包或改宿主已获授权。

## 原型交付

能写文件时，默认在用户输出目录的 `preview/` 交付独立 `index.html`；可分多个页面。使用本地内联样式、脚本和样例数据，能直接打开，不依赖 CDN、后端或 API Key。它只是设计原型，不是安装包；不要生成 manifest、规则、schema 等完整拓展来绕过确认。

原型提供三态切换与关键动作的模拟：输入或选择答案、提交显示结果／待评分、进入编辑并改变一个字段等。说明哪些保存、评分、AI、上传是模拟。图片与其他资源只读引用或复制到 preview，不能读写 `.state`，不能启动真实评分。已有拓展可以使用实际隔离渲染结果，附交互说明；若复制模拟实现，标记与实际包的差异，不能自称已验证实际运行。

桌面正文宽度、段落间距、图片比例应接近练习效果；手机视图应能阅读与操作。练习、结果和编辑采用相同正文宽度规则。共享材料与小问的对应、答案位置和选项排列要清晰，避免把整份试卷一股脑塞进一个富文本框。只允许一个活动富文本编辑器，其他字段静态显示；设计中明确怎样切换编辑目标。

图形环境不足、只能输出文本时，在回复中给三个状态的线框草图和完整交互表，说明无法提供实际可视预览，询问用户是否接受这种评审方式；不自动视为通过。没有能力制作原型时如实停在该缺口，不能用最终题库替代。

## 三态和交互表

| 状态 | 用户必须能看到／确认 |
| --- | --- |
| 未提交 | 题干与附件、小问关联、作答控件、恢复已有答案、提交条件；标准答案和私有评分依据隐藏 |
| 提交后 | 本人答案、解析和正式分数；待评分与 AI 建议明确区分，确认评分入口和再次作答的效果 |
| 编辑 | 题干、附件、答案、评分依据和满分的修改入口；保存失败／切题保留的行为及正文宽度 |

交互表写具体行为，至少覆盖该题型实际提供的输入、提交、结果／评分、再答和编辑。按需增加排序、连线、小题定位、图片调整等专用动作。示例：

| 控件／触发 | 前置状态 | 页面反馈 | 保存／判分归属 | 失败时 |
| --- | --- | --- | --- | --- |
| 选择选项 | 未提交 | 高亮当前选项，允许改选 | 页面发完整 answer 草稿，宿主保存 | 保留选择并提示未保存 |
| 提交答案 | 输入满足要求 | 显示结果或待评分，按权限开放后续控件 | 规则 grade 判分；页面不伪造 result | 保留答案并显示可重试错误 |
| 确认人工／AI 分数 | 已提交且可复评 | 正式分数与反馈更新，AI 建议清楚标记 | 规则 review／宿主确认接口 | 保留候选，提示失败或过期 |
| 编辑后切题／保存 | 编辑 | 当前修改保留，保存后能在练习看到同样排版 | 拓展导出文档／草稿，宿主持久化 | 保留未完成表单并定位错误 |

示例表不能原样当作所有题型的方案；只承诺实际安装包或现有接口能实现的行为。题库总分卡、历史列表、顶部标签和宿主导航由应用提供，原型中的宿主示意应明确标注，不让拓展负责实现它们。

## 确认与后续

回复末尾注明当前为阶段 B、展示的原型位置、尚待决定的内容，提出“请确认这份三态界面与交互，或指出要调整的地方”。未收到答复就停止，不能自行补上一句“我按此方案继续”。若先前没有展示原型，泛泛的“继续／可以”不是对未知 UI 的确认；在已展示明确原型的上下文中表示认可的答复可以采用。

用户批准后，在制作报告记录原型路径／方案摘要及用户确认依据；不要伪造确认记录。先实现少量代表题小样，对照确认稿检查三态与关键动作。修复原型和实际 UI 的差异，再批量生成。小样一致无需再次请求同一许可；新出现的结构或重大交互变更只重新确认变化部分。缺少运行工具的验证缺口必须在批量交付前告知并取得用户接受。

纯结构校验器无法证明 Agent 有没有展示设计，也无法代替用户确认。不得声称“校验通过，所以 UI 已获批准”或“skill 能强制所有外部 Agent 遵循”。
